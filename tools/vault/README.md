# vault: encrypted research paths in git

`vault` keeps chosen paths (findings, leads, session logs) encrypted in git
while every authorised session and workflow sees plaintext. It is a git
clean/smudge filter: files are encrypted when staged and decrypted when
checked out, so tools, scripts and agents work unchanged.

Status: the tool, hooks and CI action are in place. **No path is encrypted
yet.** A repository adopts vault when it commits `.vault/vault.json`. Until
then every hook here is inert.

## Read this first

1. **A private repository is stronger and cheaper.** If nothing in the
   repository needs to be public, making it private closes every channel in
   the table below at once. vault is for a repository whose code stays public
   while its findings do not.
2. **Encryption does not reach history.** A finding already pushed to a public
   repository stays readable in old commits, PR refs, forks and clones.
   Hiding it needs a history rewrite and a request to GitHub support to purge
   cached refs. Treat anything already cloned as disclosed.

## Cryptography

| Part | Choice | Why |
|---|---|---|
| Cipher | AES-SIV-256 (RFC 5297, RustCrypto `aes-siv`) | Deterministic, so `git status` reproduces the committed blob. Also safe if a nonce would repeat, because there is no nonce. |
| Associated data | `isogeny-labs/vault/v1`, repo, realm, epoch | A blob does not decrypt in another repository, realm or epoch. |
| Path binding | The path is encrypted alongside the content | Moving or swapping ciphertext is refused at checkout and by the guard. The path sits inside the payload rather than in the associated data so that `git diff` textconv, which never sees the path, can still decrypt. |
| Size hiding | Padmé padding | A file's size is revealed only to within about 12%. |
| Keys | One 64-byte data key per realm and epoch, generated by KMS (`GenerateDataKey`) | The wrapped form is committed. Only KMS can unwrap it. |
| Key binding | KMS encryption context `{repo, realm, epoch}` | A wrapped key copied to another realm or epoch does not unwrap, and IAM can grant each realm separately. |

Blob layout (frozen by `format::tests::frozen_vector`; the vector was
cross-checked against Python `cryptography`'s independent AES-SIV):

```text
"\0AVLT1" | u8 realm_len | realm | u32be epoch | AES-SIV(K, AD, u16be path_len | path | padme(content))
```

The leading NUL makes git and GitHub treat the blob as binary.

### What it does not hide

- **Equality.** The same content at the same path under the same epoch
  encrypts identically.
- **The shape of the tree.** File names, directory structure, commit times
  and the approximate size of each file stay visible.
- **Forgery by key holders.** Any holder of a realm key can produce valid
  blobs. Authorship and claims still go through pcc.
- **The past, on rotation.** A new epoch protects new commits only. Anyone
  who ever unwrapped an old key can still read history encrypted under it.

## How it behaves

| Operation | No key (locked) | Key cached (unlocked) |
|---|---|---|
| Checkout (smudge) | The ciphertext is written as is, and checkout succeeds. | Decrypted. If authentication or the path check fails, the ciphertext is left in place with a warning. |
| Stage (clean) | **Error.** `filter.<d>.required=true` makes git refuse to stage plaintext. Ciphertext in a locked tree passes through unchanged. | Encrypted under the realm's current epoch. |
| `git diff` / `log -p` | A stub line: `[vault: N bytes, realm R epoch E, locked]`. | Plaintext, through textconv. |

Each realm gets its own filter driver, `vault-<realm>`, so the attribute
names the realm. git runs one `vault filter-process` per realm for the whole
command rather than one process per file.

### Preventing leaks

The likeliest leak is a clone that never installed the filter: git then
stages plaintext without any warning. Three layers guard against it:

1. **git hooks.** `vault unlock` installs a pre-commit hook
   (`guard --staged --verify`) and a pre-push hook (`guard --pre-push --verify`).
2. **Claude Code hook.** `.claude/hooks/vault-hook.sh` runs the same checks
   on `git commit`, `git push` and `gh pr create`. It also refuses when the
   repository uses vault but the binary is missing.
3. **After merge.** `.github/workflows/vault.yml` audits the full history.
   A PR-time required check would have to join the merge set, which is the
   owner's decision (AGENTS.md, "Default workflow").

A path is protected if its `filter` attribute is `vault-*` **or** it matches
a `protect` glob in `.vault/vault.json`. Deleting a line from
`.gitattributes` therefore cannot quietly switch encryption off. With
`--verify` and the key cached, the guard also authenticates each blob and
checks its embedded path. After `git mv`, it asks you to `git add` the moved
file so the file is re-encrypted for its new path.

## Adopting it in a repository

The AWS setup is done once, by the owner. Use one symmetric KMS key in
us-west-2. The key policy grants `kms:Decrypt` for each realm, conditioned
on the encryption context:

```json
{
  "Sid": "SessionsDecryptFindings",
  "Effect": "Allow",
  "Principal": {"AWS": "arn:aws:iam::<acct>:role/claude-session-vault"},
  "Action": "kms:Decrypt",
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:EncryptionContext:repo": "isogeny-labs/crypto",
      "kms:EncryptionContext:realm": "findings"
    }
  }
}
```

Grant `kms:GenerateDataKey` only to the principal that creates keys (a
human, or an admin role). For CI, give each realm its own role. Its OIDC
trust policy pins the subject to a protected GitHub Environment:

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:isogeny-labs/crypto:environment:vault-findings"
  }
}
```

Never let `pull_request` jobs from forks, or `pull_request_target`, reach
these roles.

Then, in the repository:

```sh
cargo install --locked --path tools/vault
vault init --repo isogeny-labs/crypto --kms-key alias/autoresearch-vault \
           --protect 'research/**' --protect 'docs/session-logs/**'
vault new-key --realm findings            # KMS GenerateDataKey -> .vault/keys/findings.1.kms
printf 'research/** filter=vault-findings diff=vault\n' >> .gitattributes
git add --renormalize -- research docs/session-logs   # encrypt what is already tracked
git add .vault .gitattributes && git commit
vault export-key --realm findings --epoch 1   # escrow offline (hardware token or safe)
```

### Daily use

| Task | Command |
|---|---|
| Claude session | Nothing: the SessionStart hook runs `vault unlock` with the session's AWS identity. |
| Human | `vault unlock`, and `vault lock` when done. |
| Recovery without AWS | `vault unlock --key-file findings:1:/path/to/escrow.hex` |
| Rotate | `vault new-key --realm findings && git add --renormalize -- . && git commit` |
| Status | `vault status` |

### GitHub Actions

```yaml
jobs:
  uses-findings:
    environment: vault-findings      # protected: main only, optional reviewers
    permissions: { contents: read, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/vault-unlock
        with:
          realms: findings
          role-to-assume: ${{ vars.VAULT_FINDINGS_ROLE_ARN }}
      - run: ./do-the-work            # plaintext is in the workspace
      - run: vault seal --realm findings --label ci/out.json out.json out.json.vault
```

**Logs on a public repository are public.** A job that decrypts must print
only aggregates or pass/fail. Upload artifacts only after `vault seal`.
`::add-mask::` does not protect file contents. Prefer running decrypting
work on isolab/EKS, where logs stay in the lab's AWS account.

## Channels vault does not cover

| Channel | What to do |
|---|---|
| Paths, branch names, commit messages, PR titles and bodies, review comments | Use neutral names (`research/r-0142/`). A finding written in a PR body is public. |
| GitHub Pages, leaderboard HTML, rendered reports | Build them from plaintext only to a private destination, or publish a redacted build. |
| S3 raw data whose SHA-256 is in a public record | Use a private bucket with SSE-KMS. Keep plaintext hashes inside encrypted records: a public hash of low-entropy data can be brute-forced. |
| pcc claims and bench records | Publicly commit the ciphertext hash, which is stable because encryption is deterministic. Keep the plaintext hash inside the encrypted record. |
| research-kb, lead atlas, ecdb | These index plaintext. They must run privately, with a key. Otherwise they become the leak. |

## Known limits

- **Merge conflicts on an encrypted file** are binary conflicts. Resolve them
  in the plaintext working copy, then `git add`.
- **The `aws` CLI is required** for KMS calls. `$VAULT_AWS` points vault at
  another program.
- **The unwrapped key is cached** in `.git/vault/` with mode 0600, as
  git-crypt does. Run `vault lock` on machines that persist.

## Tests

```sh
cd tools/vault && cargo test && cargo clippy --all-targets -- -D warnings
```

There are unit tests and end-to-end tests against real git, using a fake
`aws` that enforces the encryption context. They cover:

- determinism and the absence of plaintext anywhere in the object store;
- a fresh clone starting locked, then `vault unlock` and `vault lock`;
- refusing to stage plaintext without a key (fail-closed);
- the guard catching a clone without the filter, including after its
  attribute line is deleted;
- the swap and `git mv` path checks;
- rotation, with history from the old epoch still reading;
- refusing a wrapped key under the wrong encryption context;
- `seal`/`unseal` for CI artifacts.
