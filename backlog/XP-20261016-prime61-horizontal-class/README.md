## Question

What are the factor-base results (the frozen `prime_fast` policy: native
low-x three-inverse-pair base, 20 relations requested, 12 seeds
`2026101600..2026101611`, 100,000 target trials per stream) over every
base-field isomorphism class in the fixed ordinary trace class of
`E: y^2 = x^3 - 3x + 111` over `p = 2^61 - 1`?

## How many classes, and which degree set covers them

*Recorded* ([prime61 study](../../research/prime61_isogeny_20261016/README.md)):
`D = t^2 - 4p = -6649310858224389603 = -3 * 97 * 113 * 35831 * 5643470711`,
fundamental, so every curve in the class has the maximal order and the
vertices are the `h(D)` j-invariants. The exact form `A = (7, 5, 237475387793728201)`,
the class of a prime above 7, has exact order **68,162,026 = 2 * 34081013**
(native-checked GP reduced-form certificate). PARI's GRH-conditional output
is `h = 545,296,208`, structure `[68162026, 2, 2, 2]`.

*Derived* (design-time calculation; replayed natively by code item C1 below
before freeze). Five prime discriminants give four independent genus
characters, so `Cl(D)/Cl(D)^2 = (Z/2)^4` unconditionally (genus theory).
Using the characters for 97, 113, 35831, 5643470711, the selected degrees
map to:

| prime | 3 (ramified) | 7 | 11 | 13 | 19 | 23 | 53 | 61 |
|:--|:--|:--|:--|:--|:--|:--|:--|:--|
| genus vector | 0100 | 1001 | 0010 | 1001 | 1111 | 1101 | 0010 | 0011 |

`{3, 11, 61}` together with `7` span all of `(Z/2)^4` (rank 4). The subgroup
`H` generated by the degree set therefore surjects onto the genus group and
contains `A^2` of odd order 34,081,013, so
**`|H| >= 16 * 34,081,013 = 545,296,208` unconditionally.** If PARI's `h` is
right, the degree set `{3,7,11,13,19,23,53,61}` generates the whole class.
That `h` is not exceeded still needs an unconditional certificate (code
item C2); until then "every class" means "every class in `H`, which has at
least 545,296,208 elements and is all of them if `h = 545,296,208`".

This lifts the certified vertex lower bound from 68,162,026 to 545,296,208.
The envelope below uses `N = 545,296,208`.

## Traversal: eight ℓ = 7 cycles instead of one full-degree BFS

The current card argv (a full-degree BFS on one SQLite writer) is sound but
cannot finish: *derived* from the probe, 545,296,208 expansions at
0.2024 s each is 1,278 days on one writer, and measurement on one database
is serialized by its write lock (below).

Instead (PROTOCOL.md §3): `<[l_7]>` has 68,162,026 elements and the eight
products `p_3^a l_11^b l_61^c` (`a,b,c ∈ {0,1}`) have genus vectors that
are distinct modulo `<1001>`, so they lie in eight distinct cosets of
`<[l_7]>` (unconditional). Each coset is one ℓ = 7 cycle of exactly
68,162,026 j-invariants. The eight cycle roots are curves 1, 2, 5, 15, 19,
29, 66 and 164 of the committed pilot dump
(`research/prime61_disk_walk_20261017/results/pilot/dump-32.stdout`), with
their verified transported `G, Q`; they are frozen as
[specs/coset-0.json … coset-7.json](specs/) (`primes: [7]`, all other
spec fields identical to the pilot). All eight pass the binary's
`Spec::validate` (`probes/coset-spec-init.jsonl`). Each cycle runs with the
**existing** `isogeny_disk_walk advance` on its own database, in parallel.
A closed cycle with exactly 68,162,026 curves and 136,324,052 edges replays
the order certificate of `A` independently.

### What fits on this host (32 vCPU Xeon 6975P, 124 GB, 2 TB EBS, spot)

- **Stages 1 and 2 fit now**, once C1 and C2 exist: 716 core-hours, 8
  processes, 562 GB, 7–83 days wall bound by fsync latency (C5 would bring
  it to ≈ 4 days). This alone answers the class-coverage half of the
  question: all 545,296,208 vertices with verified transported `G, Q`.
- **Stage 3 does not fit in a reasonable time:** 217,361 core-hours is
  about nine months of the whole host, longer while it is shared. It
  needs a fleet (for example 1,000 vCPUs for ≈ 9–10 days) or an owner
  decision to change the per-vertex workload. Shrinking the workload or
  sampling vertices would be a different experiment and is not proposed
  here as a substitute.
- Disk fits (≈ 1.0 TB of 1.9 TB free) only if completed measurement shards
  are gzipped; raw it is 1.7 TB, too close to the other experiments' needs.

### Checkpoint and resume

The implementation **resumes**: rerunning the same `advance` or `measure`
argv on the same database continues from the last committed transaction
(one source expansion, or one measurement stream), and `open` refuses a
changed spec. A spot *reboot* or *stop* keeps the EBS volume, so an
interruption loses at most one transaction per process (< 0.1 s of CPU for
enumeration, ≤ 0.12 s for measurement). A spot *termination* that deletes
the volume loses everything not copied off-host. S3 is denied to this
instance role and Drive uploads go through a session-bound connector, so
there is no automatic off-host copy today; PROTOCOL.md §4 makes each
measurement shard a small self-contained database (≈ 40 MB gzipped) so
that off-host copying, when available, bounds a termination's loss to the
shards in flight. The card's `resume_flag` stays null because the CLI has
no flag: resume is implicit.
