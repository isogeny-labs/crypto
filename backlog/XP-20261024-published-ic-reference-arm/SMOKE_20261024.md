# Smoke run, 2026-10-24: relation-level reference-arm cell, not a solve and not a claim

Harness: `examples/ref_arm_smoke_f2.rs` (this commit), built with
`CARGO_TARGET_DIR=/Volumes/SSD990-2/cargo-target-ic-followthrough-20261024 cargo build --release --example ref_arm_smoke_f2`
(cold lib build 34 min under load). Rows: [`smoke_rows.jsonl`](smoke_rows.jsonl)
(command: `ref_arm_smoke_f2 <n> 6 20261024 <a>`; seed 20261024; caps `ulimit -t 1800`; memory never
approached 8 GB, msolve peak not measured).

## What ran

Koblitz curves, m = 3, base **`F_u = {P : u(P) in V}`, `u = 1/(x+1)`** with `V` a random non-Frobenius-invariant
subspace containing 1, dimension l = ceil((n+1)/3) (`random_subspace_containing_one`,
`build_symmetrised_factor_base_from_basis`); system = **u-frame 2-torsion invariants only, no `e_i`
reduction** (`symmetrised_terms(3)`, 18 terms, per-point `w_i` of degree 2; the lab's construction from
`RESEARCH_EXOTIC_COORDINATES.md`, **not** the FGHR `S_m`-symmetrised system and not the standard x-base),
field equations `x^2 + x` appended, solved by **`/opt/homebrew/bin/msolve` v0.9.5, `-g 2 -t 1`** over GF(2).
Per cell 6 targets: 3 uniformly random curve points, 3 planted as a sum of three base points (positive
control). Verdict from
`gb_is_one`; on a non-unit ideal roots were extracted and lifted and `fb.sum == R` (or `R+T`) was
checked in the group. Cross-check: the repo's exhaustive `enumerate_symmetrised`.

`a = 1` at n = 13 is refused by `KoblitzCurve::new` (first attempt panicked), so n = 13 is the
`a = 0` curve. CPU is child `rusage` (user + system) at **host load ~100 or more**; contention inflates it

n = 13 to n = 15 with the same m, and the drop at n = 17 (more equations than unknowns), are
consistent with system shape, not with n; I did not investigate.

## What was improvised, and what that means for the build list

1. **Curves are Koblitz only.** The symmetrised generator is Koblitz (`u = 1/(x+1)`, F_2 coefficients);
   there is no random-binary-curve instance builder in the module. The ladder's random-binary
   `icv1-f2m*` ids were therefore not attempted. -> M1, M4.
2. **Plain msolve, no framework.** msolve was shelled out, not a `SystemSolver`. -> M2.
3. **Root extraction by evaluating all `2^n_vars` assignments** (13 to 16 unknowns). This is the
   cheat that makes the cell run; it is the cost that real extraction (FGLM / parametrisation) would
   add and is **not** in the CPU column. msolve supporting a rational parametrisation at p = 2 is
   unverified. -> M2.
4. **Only the oracle**: no relation collection until rank, no linear algebra, no discrete log
   recovery, no `[d]G = Q` check. The "answer verified" here is "the relation sums to the target".
   The whole-solve harness is M5, and was not attempted.
5. **No GAE hook.** There is no unit for an external process (`INVENTORY` M6); the only quantity
   recorded is child CPU seconds, which is the secondary, non-admissible quantity of PROTOCOL §4.
6. **Not the FGHR `S_4`, not the x-base** (see above); the `e_i`-symmetrised `binary_semaev_s4.rs` is the M1 starting point. **FGHR variable choice (Galbraith-Gebregiyorgis special subspace) was not applied**; V is a
   uniformly random subspace through 1. Frobenius invariants not used (non-invariant V).
7. **m = 4 not attempted:** `symmetrised_terms(4)` returns `None`.
8. **WDSat not attempted** (not installed; no network fetch of the code was done).
9. msolve is v0.9.5 here; the lab's m = 4 cards pin v0.6.5.

## Reading

The plumbing for a binary m = 3 cell exists and the lab's u-frame system and u-base are real code that agrees with enumeration; they are not the published reference construction. The gap to an admissible reference row is
M2 (root extraction), M5 (whole solve) and M6 (pricing), not the polynomial. Nothing here compares
to rho or to a lab producer.
