Faster fixed-width multiplication for generic-prime ECC scalar multiplication (2026-11-25)

Branch feat/lucid-cray-tckh5e, PR isogeny-labs/crypto#5173. Benchmark record benchmarks/records/20261125T1820Z-mont-mul-kernels.json. Status of every number below: unverified assertion (local single-host measurement, no pcc claim, no independent replay).

Boundary

What is measured: wall time of one scalar multiplication k·P (random k < 2^bits(p), random affine P, random curve coefficient a) through the fixed-width Montgomery path src/ecc/mont_vt.rs behind Point::scalar_mul and Point::scalar_mul_vartime, including entry to Montgomery form, the ladder, the final inversion and the conversion back to BigUint. Also the latency of one dependent modular multiplication / squaring / inversion per width.

Not measured, not changed: the P-256 and secp256k1 paths (they have their own specialised ladders and are dispatched before mont_vt), single-word primes (the Word path), the constant-time scalar_mul_ct, binary fields, and any ECDLP solver. This is a component speed-up of public-input scalar multiplication (set-up multiplications of walks and searches, signature verification on curves other than P-256/secp256k1); it says nothing about the cost of ECDLP and is not an index-calculus row.

Fields (one per limb width): 2^127−1 (2 limbs), P-192 (3), 2^255−19 (4), the largest prime below 2^320 (5), P-384 (6), Goldilocks 2^448−2^224−1 (7), the largest prime below 2^512 (8), 2^521−1 (9).

What changed

exact limb widths 5..8 (were padded to 9 limbs: 81 word products per CIOS pass instead of 25–64) Point::scalar_mul dispatch every 5..8-limb modulus bit-identical for every odd modulus

width-4 (≤ 3 limbs) / width-5 NAF; odd multiples built on the isomorphic curve scaled by Z(2P) (so 2P is affine without an inversion) and normalised by one batch inversion Mont::ladder_wnaf scalar_mul_vartime, multi-word primes equal over a prime; declines to the binary ladder on a small-order base or non-unit Z
one-level subtractive Karatsuba product Mont::mul_wide_karatsuba measured only, not used —

Point::scalar_mul’s contract (“the same point the BigUint ladder returns, for every odd modulus”) is unchanged, so only the bit-identical changes go there. Point::scalar_mul_vartime documents “exactly scalar_mul over a prime p”, which the wNAF and binary-GCD changes keep. The fast vartime path runs only on moduli that pass Miller–Rabin (40 fixed bases, cached per thread for the last eight moduli); a composite multi-word modulus runs scalar_mul itself, so the existing test composite_modulus_non_units_match_constant_time (strict equality on (2^31−1)(2^89−1), where the final Z is a unit) keeps holding. It failed on the first version of this change, which is how the gap was found.

Method

src/bin/mont_mul_bench.rs, taskset -c 3 on a 4-vCPU Intel Xeon @ 2.10 GHz cloud VM (no hardware PMU, isolation: local container). Per field: 41 rounds; each round draws 30 fresh scalars and runs every arm on the same scalars, arm order shuffled per round from a derived seed; an A/A copy of the baseline arm (pad9_cios#aa) measures the noise floor. Speedup = baseline ns / arm ns per round, summarised by the median and a 2000-resample percentile bootstrap 95% interval. Before timing, every arm and both production entry points are checked equal to the num-bigint ladder on 38 scalars per field (edge values 0..256, p−1, 2^bits−1, 2^(bits−1), 24 random); the run aborts on any mismatch. Kernel latency: 7 repetitions of 2·10^6 dependent operations (10^5 for num-bigint, 2·10^3 for inversions), median.

Four runs, all under the one benchmark record:

  • run 1 at f0271142f: kernels and arms;
  • run 2 at 8427dc0c1: the first tuned kernel;
  • run 3 at 8fc62fdc3: the final tuned kernel;
  • run 4 at 17c530427: the final code, including the Miller–Rabin gate of the vartime path.

Run 2 showed that the first tuned kernel regressed scalar_mul by 1–3% at 2–3 limbs end to end. That kernel used the SOS product and dedicated squaring at N ≤ 3, chosen from the isolated kernel loop. Run 3’s kernel keeps plain CIOS there. The runs agree to within about 1–2% on every common paired ratio. Absolute times move between runs (shared VM, baseline 24–31 µs at 2 limbs), which is why every comparison is paired within a round.

Reading

  • Most of the scalar_mul gain at 5–8 limbs is the dispatch fix, not a new multiplication algorithm: those moduli were paying for 9-limb arithmetic.
  • Asymptotically fast multiplication does not pay at these sizes. One Karatsuba level saves N²/4 word products but adds carries, two absolute differences and a recombination, and on this host it lost 3–30% per product at N = 4, 6, 8 (and 7% per k·P at 4 limbs). Toom-Cook, Schönhage–Strassen and Harvey–van der Hoeven have crossovers in the thousands to millions of bits; ECC fields are 2–9 words. The levers here are fewer word products (squaring), the right width, fewer inversions, and fewer point additions.
  • For variable-time public scalars the larger lever is the scalar side (wNAF: ~bits/6 additions instead of bits/2) together with an inversion that is cheap enough to normalise a precomputed table.

  • cargo test --lib -- ecc::mont_vt ecc::point: 26 passed. Whole ecc:: module: 345 passed, 2 ignored.
  • The 40 modules outside ecc that call scalar_mul / scalar_mul_vartime: 1093 passed, 49 failed. All 49 are pre-existing in this sparse checkout: 36 panic on data files under research/ that are not checked out, and the other 13 fail identically on the pre-change point.rs / mont_vt.rs (rebuilt and rerun one by one).
  • The benchmark’s correctness gate (every arm, scalar_mul and scalar_mul_vartime equal to the num-bigint ladder on 38 scalars per field) passed in all four runs.
  • Build note: the library test target needs more than this container’s ~15 GB with debuginfo; it was built with CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 CARGO_PROFILE_DEV_CODEGEN_UNITS=64 -j 1.

Not done / open

  • No ADX/MULX (adcx/adox dual carry chains) assembly kernel; the host has adx and bmi2. That is the next measurable lever for the product itself (it is how the fastest libraries reach ~2× over portable CIOS at 4 limbs).
  • No “no-carry” CIOS variant for moduli with spare top bits (applies to 2^521−1 here, and to BN254/BLS12-381-style primes).
  • scalar_mul_ct (secret scalars) still runs FieldElement on num-bigint for generic primes; it was not touched.
  • Single host, no PMU (cycles/IPC unavailable), not run on Iso Lab EKS; no independent replay. An EKS rerun of mont_mul_bench would make the numbers lab-grade.
