# Iso Lab connections for agents

The checkout registers **`isolab`** (NATS) and **`isolab-eks`** (EKS) in
[`.mcp.json`](../.mcp.json) for Claude Code and
[`.codex/config.toml`](../.codex/config.toml) for trusted Codex projects.
Install the client once on each agent host and supply its existing connection
settings. Restart the agent session after configuration so it loads the servers.
Installation and configuration are not evidence of a reachable lab: run the
read-only connection check before submitting work.

| Connection | Required access | Tools and measurement contract |
| --- | --- | --- |
| `isolab` | Existing NATS hub URL plus its token or credentials file; network route to that hub | `isolab_overview`, `isolab_submit`, `isolab_result`, etc.; `isolab.job/v1`, including the existing strict policy |
| `isolab-eks` | Dedicated kubeconfig, explicit context, authorized AWS identity and route to the EKS API | `isolab_k8s_overview`, `isolab_k8s_benchmark`, etc.; native ecbench L2 on the existing Spot pool |

These are separate backends. A legacy NATS job such as the unsubmitted job in
PR #2513 cannot be sent to `isolab_k8s_benchmark`. The EKS deployment's current
image and binary hashes determine which code it can execute; it does not compile
a caller's revision or supply an `isoclass-rho` binary automatically. Neither
connection creates a load balancer or changes an endpoint allowlist.

## NATS lab

Install from this checkout with Python 3.11+ and `uv` available:

```sh
bash scripts/isolab-agent.sh setup nats
```

Set `ISOLAB_URL` to the existing hub's address (`nats://HOST:4222`, or `tls://`
when that hub supports TLS). Supply `ISOLAB_TOKEN` through the environment's
secret settings, or set `ISOLAB_CREDS` to an existing readable NATS credentials
file. `ISOLAB_NAMESPACE` is optional; its existing default is `ISOLAB`.
Do not put token values in project files, shell arguments, PRs or chat. The
client also accepts credential-bearing URLs, but the separate token variable
keeps the address non-secret.

```sh
bash scripts/isolab-agent.sh check nats
```

This reads the worker roster with a 30-second deadline. An empty roster means
the hub answered, not that a worker can accept a strict job. In the agent, call
`isolab_overview`, inspect worker readiness, then use the existing
[independent-runner workflow](../.agents/skills/ecbench-independent-runner/SKILL.md).
Strict placement and binary compatibility still need verification.

The launcher requires an explicit hub URL; it does not invent a localhost hub.
For an already installed client, `ISOLAB_BIN` selects an absolute executable
path. The project MCP connection forces stdio regardless of any ambient
`ISOLAB_MCP_TRANSPORT` setting.

## Existing EKS lab

Install the native connector from this checkout with Rust available:

```sh
bash scripts/isolab-agent.sh setup eks
```

Supply `KUBECONFIG` as an absolute path to the dedicated lab kubeconfig and
`ISOLAB_KUBE_CONTEXT` as its exact context. Configure an authorized AWS identity
using the host's usual profile, workload identity or injected temporary
credentials. Runtime tools are AWS CLI, kubectl, jq, Bash and GNU timeout.
An existing installation can be selected with an absolute `ISOLAB_MCP_BIN` path;
keep its matching `submit-job` next to the executable.

```sh
bash scripts/isolab-agent.sh check eks
```

This calls `isolab_k8s_overview` with a 60-second deadline. It reads Jobs and
does not submit a benchmark or create capacity. After it passes, call overview
in the agent and use the EKS deployment's
[native connector instructions](../taskq/deploy/eks-karpenter/README.md#native-mcp-connector).
The documented context and paths in that guide belong to the existing harness;
another host needs its own authorized configuration. No static Kubernetes
token or replacement AWS key is generated by this setup.

For agents without a route to the Kubernetes API, the existing
[portable CodeBuild/Actions interface](../taskq/deploy/eks-karpenter/HARNESS.md)
can submit through the private network. It still needs the documented authorized
AWS identity or repository Actions write access. It is not silently selected
by the direct EKS MCP connection.

## Fresh sessions and other clients

`scripts/setup-workstation.sh --only isolab` installs only the backends whose
connection variables are set. The existing Claude cloud SessionStart hook runs
that setup component after installing toolchains. Set variables in the shared
agent environment so future sessions inherit them. With neither connection
configured, setup reports that fact and downloads neither client.

If a minimal sparse checkout has left client sources off disk, materialize the
needed paths before setup (the default cloud `harness` profile keeps them):

```sh
scripts/sparse-checkout.sh add --path isolab/ --path taskq/deploy/eks-karpenter/
```

Clients live under `target/isolab-agent/` (ignored by Git).
`ISOLAB_AGENT_STATE_DIR` can select another absolute directory. Run setup again
after updating the checkout to rebuild/reinstall the clients. MCP startup never
installs packages or starts a hub, worker, benchmark, key-creation or login flow.
With `WORKSPACE_OFFLINE=1`, setup refuses downloads; use preinstalled binaries
and existing private endpoints instead.

Codex forwards the named connection, AWS identity and proxy environment
variables from its launching process; no credential values are saved in the
project configuration. For another stdio client, use:

```text
command: bash
args: [/absolute/path/to/crypto/scripts/isolab-agent.sh, mcp, nats]
```

Use `eks` in the last argument for the EKS connector. Give the child process the
same environment variables listed above. stdout is MCP only; diagnostics go to
stderr. Connection checks suppress library errors that might contain tokens.

## Access failures

Missing credentials, an unreadable kubeconfig, no compatible worker, a rejected
AWS identity and a blocked network route are different blockers. Read the
existing host's configuration and network policy; request the missing binding
or authorized route rather than creating replacement keys or a new hub.
NATS uses its hub's TCP port, and EKS uses HTTPS: an HTTP host allowlist alone
does not establish NATS TCP access. Follow the environment's supported TCP/VPN
configuration instead of bypassing its proxy.

This repository wiring does not attach MCP tools to an already running hosted
agent turn. Restart a client that loads project configuration, or attach these
servers through the hosted environment's MCP settings. A successful tool catalog
handshake alone establishes discovery, not authenticated lab access or timing.
