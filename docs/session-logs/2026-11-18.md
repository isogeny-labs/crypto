## Table-build speed-up analysis (`[pcc:unverified]`, no code change)

### What was done
- Read `build4` (examples/prime_fast_j0_multi4.rs): the triple-sum table already uses one `batch_inv` per (i,j,m,s1) over 3(B-j-1) denominators, sharing one inverse between the sum and difference x-coordinates; about 78 ns per table entry at B=44 (37 ms, ~477k entries). Holdout T=64 split (row 0): build 37.3 ms, collection 10.7 ms, per-target 10.6 ms, total 58.7 ms.
- Estimate (not measured): merging the six (m,s1) batches into one batch per (i,j) would save about 1.4 field-mult-equivalents per entry, about 5% of build, below the +-20% single-host noise.

### Decisions made
- Not implemented: even removing the whole build (37 ms) leaves 21 ms vs BSGS 24.7 ms at T=64, so build is the entire gap there, but a 5% saving cannot close it and could not be resolved with this noise. A gain needs a structurally smaller table (fewer entries per unit of relation yield), not faster entries. Next discriminating experiment: partial table (store only entries whose canonical key hashes into a fraction f of the space, scan with matching filter), which cuts build by 1/f and collection by the same factor; predicted break-even at T=64 needs f<=0.5 with extra candidates per relation x2, i.e. no net gain unless the build, not the candidate loop, dominates. To be tested before any claim.

## Partial-table lead closed by analysis (`[pcc:unverified]`, no run)

### What was done
- Checked the partial-table idea against `build4`: an entry's canonical key is only known after the point sum is computed, which is the cost being saved. Skipping entries therefore cannot reduce build cost; restricting which triples (i,j,l) are built is the same as shrinking B, which the B4 tuning grid (B=20..80, `multi4_tune/`) already covers.

### Decisions made
- Lead closed without an experiment: it is not a new design, only the already-tuned B trade-off. Recorded as an obstruction. No run, no claim.
- Remaining levers with a real chance at the T=64 gap to BSGS (build is ~64% of sym4 time): (a) a table keyed by a cheaper hash of a partial sum (e.g. precomputed pair sums joined with single points, so each triple costs a table probe instead of a point addition: meet-in-the-middle from the scan side, trading build for more scan probes); (b) amortise the build across curves sharing a factor base (not applicable: tables depend on the curve). Next experiment: (a), predicted to move cost from build to collection; needs a model before code.

## Pair-table meet-in-the-middle model: no gain predicted (`[pcc:unverified]`, model only)

### What was done
- Modelled lead (a). Current scheme: triple table (~6B^3 entries, one point addition each) probed by single-candidate scan (R +- phi^k f_h). A pair-sum table probed by pair candidates has table ~6B^2, so per-relation cost p/B^2 per candidate (the 3-summand cost), worse; a pair table probed by single points is the existing scheme with the roles swapped. For B relations: build B^3 + scan B*p/B^3 candidates, optimum B^5 ~ p, exactly the already-tuned p^(3/5) trade-off.

### Decisions made
- Closed: it only re-labels the existing balance, no prototype. Remaining gap to folded BSGS at T=64 is therefore a constant-factor matter in the build (about 78 ns/entry) or needs a different structural idea (e.g. exploiting the +-/orbit structure to shrink entries per relation, or sharing one table across many R values, which the multi-target scan already does).
- No improvement over the strongest baseline (folded BSGS) exists; claims stay limited to the tuned library baseline.

### Open threads
- PR #4645 CI, f4_fp.rs decision, large JSONL to artifact store, AWS-blocked gate artifacts, structural idea beyond B^5~p. Goal unmet.
