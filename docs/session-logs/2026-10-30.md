## BTN prime-field study: setup bottleneck (AKS primality)

### What was done
Investigated why the d=131 `size-json` build hung (54 min CPU, no output). Added `multtime`/`primetime` modes to `btn-prime-scaling`. Findings: Fourier integer-multiply network construction is fast at every width (8-bit 229us → 1024-bit 9.95ms, linear). But `is_prime` (arithmetic.rs) dispatches to a fast u64 path ≤64 bits and AKS above: ≤64 bits ≤17us, 65 bits (AKS) did not finish in 180s. `Curve::new`/`FactorBase::new` certify the prime, so no curve with a >64-bit prime (ECCp-131 is 131-bit) can be set up — the hang was AKS, not construction. Folded into report.json (`setup_bottleneck`), report.pdf (new section + 4th plot panel), native/README.

### Decisions made
Corrected the earlier "construction impractical at d=131" note — it is AKS primality, not network construction. Did not modify the locked crate; reported the bottleneck with a proposed fix (BPSW + Pocklington/ECPP certificate would take setup from "never" to ms while keeping certified primality). Offer to implement as a separate carefully-scoped crate change (paired-repo byte-identical) if the owner wants.

### Open threads
AKS→certified-fast primality is a real speedup opportunity for instance setup, pending owner decision. The two blockers in order: (1) prime certification >64 bits (AKS), (2) recursion crossover ≥2^131070 edges; neither near feasible.
