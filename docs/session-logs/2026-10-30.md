### What was done (commands, files, features)

Added a second elimination order for the relation network.
`relation::mitm_find_relation` enumerates the first half of the factor bases
into a table keyed by the partial sum and looks up the complement from the
second half, so one attempt costs about |F|^(m/2) + |F|^(m/2) point additions

## 2026-10-30T04:20:00Z - ecdl-tensor-ic: sparse linear algebra

### What was done (commands, files, features)

`linalg::left_kernel_vector_sparse` replaces the solver's dense elimination.
A relation row has only m nonzeros, but the dense version built a
k x (ncols + k) coefficient matrix and did O(k^3) work; the sparse version
keeps each row as a sorted `BTreeMap` (data columns plus the identity block
that records the combination), pivots smallest-first on data columns only, and
reduces each row against the stored pivot rows. It returns the same thing: a
nonzero c with sum_j c_j row_j = 0 (mod r). The dense function stays as the
reference. `tests/sparse_linalg_test.rs` (3 tests) cross-checks the two on 300
random systems, exercises rank-deficient systems whose dependency involves more
than the last row, and runs a 2000-column, 2001-row, 3-nonzero system, which
finishes in under a second.

Verified: `cargo fmt --check` clean, `cargo clippy --all-targets --
-D warnings` clean, `cargo test` 34 passed.

### Decisions made (and why)

Do this before packed table keys: with meet-in-the-middle relation search a
solve is tens of milliseconds at b = 12, so the contraction's constant factor
no longer dominates, while the dense elimination becomes the wall as N grows
(N is about 2 sqrt(2r), so O(N^3) is the first thing to break). Keep the dense
version exported so the property test has an independent reference. Pivot on
data columns only, exactly as the dense code does, so the combination semantics
are unchanged.

## 2026-10-30T05:10:00Z - ecdl-tensor-ic: parallel relation search

### What was done (commands, files, features)

With meet-in-the-middle relation search the solver now draws a batch of
targets in order, then evaluates them on `Solver::threads` workers (0 = one per
available core, 1 = sequential; `ecdldemo -threads N`), and keeps the hits in
target order. The batch size depends only on the number of relations still
missing, so every thread count draws the same targets and the outcome is
identical. Target computation `[u]P + [v]Q` moved inside the workers, so only
the scalar draws are sequential. `opcount::active()` keeps the search on one
thread while a tally is running, since the tally is thread-local and the
ecbench arm's counts must stay complete.
`tests/parallel_relations_test.rs` (3 tests) checks 1-vs-4-thread equality
(secret, relation count, attempt count, factor-base size), that the tally path
stays charged, and prints the sequential/parallel timing.

Measured on release builds, b = 20, m = 2, `-seed 7`, by timing the phases:
factor base 156 ms, relation search 439 ms sequential vs 123 ms on 8 threads
(3.6x), sparse elimination 86 ms. Whole-solve phases 681 ms -> 365 ms (1.9x);
the remaining sequential part is factor-base listing, which is O(p) square
roots at toy sizes. `ecdldemo` wall time is dominated by toy curve generation
(naive point counting), not by the attack, and is not used as evidence.

Verified: `cargo fmt --check` clean, `cargo clippy --all-targets --
-D warnings` clean, `cargo test` 35 passed (12 + 7 + 7 + 3 + 3 + 3).

### Decisions made (and why)

Determinism over load balance: target draws are fixed before dispatch and
results are collected in target order, so a replay reproduces the same
relations whatever the core count. Parallelism is skipped while tallying
instead of teaching the tally to aggregate, which keeps the ecbench arm's
accounting unchanged and deterministic. Scheduling parallelism after MITM
landed avoided stacking a third branch on an unmerged one.
