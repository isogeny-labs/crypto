# V3: oracle-free linear algebra, the real pulled-back instance, solve certificates

Run: `chained_transfer_bench run --json results_v3.json --certs certs_v3.jsonl`
under bench record `benchmarks/records/20261112T0341Z-chained-prime-transfer-v3.json`
(left open). Raw files: `results_v3.json`, `certs_v3.jsonl`; verifier output
`certs_v3.verify.txt`; run log `v3_run.log`. Every number below is a
`[pcc:unverified]` assertion; the certificates are the evidence a reader can
re-check.

## What changed

- **F4 (linear algebra was handed the answer).** `genus2_index_calculus` no
  longer calls `target_is_x` (the uncharged BSGS answer). It runs the new
  `solve_linear_free`, which returns the first zero-factor-base row's
  `x = -alpha/beta` without consulting anything about the true log, and `None`
  only when elimination finds no such row. The old gated path is kept as
  `genus2_index_calculus_oracle`. A wrong log is returned as wrong; a unit test
  shows the free path returns a doctored row's wrong value where the gated path
  returns `None`. [pcc:unverified]
- **F5 (the solved instance was a surrogate).** The bench now solves
  `(G, T) = (phi^*(P), phi^*([x]P))`, the transported pair from the verified
  pull-back chain, with rho on `J(C)` and with IC. `jac_instance` is no longer
  used by the bench. The order-`r` part of `J(C)` is cyclic when `r^2` does not
  divide `#J = #E1 * #E2`: `r` is chosen with `r^2` not dividing `#E1`, and
  candidates with `r` dividing `#E2` are skipped, so the condition held for every
  candidate that reached a solver. Each row carries `instance_type = "pullback"`.
  [pcc:unverified]
- **F14 (no solve certificates).** Each solved log, for all four arms (rho on E1,
  rho on E1', rho on J(C), IC on J(C)), is written as a
  `chained.solve.certificate/v1` record (schema in the `certify.rs` module doc;
  no existing repository schema fits an ECDLP solve claim). `verify_certs`
  re-checks `certs_v3.jsonl` from the curve data alone using only `certify.rs`:
  `G != 0`, `[r]G = 0`, `[k]G = T`, and for transferred instances
  `[k]src_g = src_t` and that the re-evaluated map sends `src_g` to `G` and
  `src_t` to `T`, hence `phi^*([k]P) = [k]phi^*(P)`. [pcc:unverified]
- **No selection on solver success.** v2 kept the first candidate whose solvers
  all succeeded. v3 takes the first candidate that passes the structural checks
  and reports the row whatever the solvers return. [pcc:unverified]
- **Transfer cost.** Building the cover or isogeny and evaluating `phi^*` is a
  one-time cost (with a trapdoor it happens once) and is in no per-instance
  figure here, v2 or v3. It is not reported separately because the bench does not
  measure it.

## Certificates

16 issued (4 arms at 4 sizes), 16 verified, 0 failed, 0 without a claim, 0
unparseable, by `verify_certs` on `certs_v3.jsonl` (output in
`certs_v3.verify.txt`); the bench's in-process re-check also gave 16 of 16.
[pcc:unverified] Claimed logs by size: 8 at p=211, 5 at p=419, 45 at p=821, 375
at p=1619, each equal to the planted `x`. [pcc:unverified]

A first run under the same bench record produced 0 of 16 verified: the new
independent elliptic-curve adder returned infinity when its accumulator was the
identity (a bug in `certify.rs`, not in a solver). It was fixed and the run
repeated; the record lists both commands, the files above are from the second.
That failure is also evidence that the verifier can reject. Unit tests cover a
good certificate and tampered `k` and `T` for both group types.
[pcc:unverified]

## Comparison to v2

- Same curves and planted logs: the candidate counter and `x` agree with
  `results_v2.json` at all four sizes. [pcc:unverified]
- Identical, as expected: rho on E1 (428, 357, 370, 847), rho on E1' (530, 562,
  274, 649) and LA mulmods (14,633; 51,976; 164,828; 603,721). The rho arms on
  E1 and E1' never touched the changed code. The LA count is the elimination's
  operation count on a matrix of the same shape; it equals the column count
  times the row count in all four rows, so it does not depend on which divisors
  the relations came from. [pcc:unverified]
- Different, because the instance is different (F5): rho on J(C) (v2 396, 497,
  389, 560; v3 396, 361, 414, 869) and IC group ops (v2 3,700; 8,315; 11,596;
  33,196; v3 3,419; 8,475; 11,353; 34,521) and trials. v2 solved a surrogate
  generator; v3 solves `phi^*(P)`, a different generator of the same cyclic
  subgroup, so the walk and the relation sequence change. The p=211 rho on J(C)
  count coincides with v2 (396). [pcc:unverified]
- IC/rho at 0 GAE moved from v2's 8.6, 23.3, 31.3, 39.2 to 8.0, 23.7, 30.7,
  40.8, a change of at most 1.6 in either direction. There is one seed per cell and no
  IC spread was measured, so the change is not interpreted. No
  conclusion changes: IC stays above rho at every price. [pcc:unverified]
- F4 changed the correctness evidence, not the counts: in v2 a wrong
  elimination would have returned `None`; in v3 it would return a wrong log and
  its certificate would fail. All four IC logs were right. [pcc:unverified]

## Limitations

- The J(C) group law inside `verify` is the library's Cantor `add` and `double`;
  only the scalar-multiplication loop is new. No second Cantor implementation
  was written, so a Cantor bug shared by solver and verifier would not be seen.
  The elliptic-curve checks use separate affine code. [pcc:unverified]
- The transfer re-evaluation reuses `Bielliptic::pull` and `VeluIsogeny::eval`;
  it checks the instance against the map as implemented, not the map against
  the mathematics. [pcc:unverified]
- One candidate curve and one seed per size; no spread. [pcc:unverified]
- `r` is a prime of 7 to 9 bits, so the sizes are small; the IC factor base is
  the whole degree-1 set. [pcc:unverified]
- No timing claim, no isolation tier, no validation-gate admission, no pcc
  claim id yet; the record is open and its raw files are not uploaded to S3.
  [pcc:unverified]
- The 16 certificates do not cover the `tower` or `amortized` experiments of
  other work in this tree. [pcc:unverified]
