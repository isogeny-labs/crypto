# ksum m = 6, 7: sizing pilot (2026-11-15) [pcc:unverified]

**Pilot only, not data.** Every number below is an unverified assertion
[pcc:unverified]: one round, 32 public targets per arm, no replicates, no A/A
arm, no replay certificate, no validator. The runs were launched with
`BENCHREC_SKIP="sizing pilot, not data"`, so there is no `bench.record/v1`
record and nothing here may reach the leaderboard or `benchmarks/`.

## Question

`ksum:m=3|4|5` builds a negation-folded table of every signed m-sum of the
base and probes each walked target once. The task estimated that a larger m
would let N shrink (cost about `sqrt(2 r (N+1))`) and gain about 5 % over the
frozen ksum5 size of the two Table B k-sum studies. Does m = 6 or 7 beat ksum5
by at least 5 % at every weight (w = 0, 0.1, 1 GAE per native operation)?

## Code

`KSumTable` / `KSumOracle` and every m-check (`plan_check`, `prepare_ksum`,
`ksum_sum_bound`, the `methods.rs` help text) already accept k = 3..9 since
35e9bf774a (per-k index width: 12 bits for k <= 5, unchanged, and 64/k bits
above). The counting is the same kind as for m <= 5: one group addition per
partial sum, built level by level, every insert counted, and a probe costs one
lookup plus `m - 1` confirming additions. This pilot's commit adds the missing
end-to-end tests:

- `ic_framework::tests::ksum_oracle_recovers_logs_with_three_to_seven_summands`:
  the pipeline recovers the planted log with m = 6 and 7 (base of 10 abscissae).
- `ecbench::known_log::tests::ksum_tables_recover_every_nonzero_prime_log`:
  recovers every nonzero log for k = 3..7.
- `plan_check_agrees_with_prepare_and_prepare_ksum`: checks k = 7 as well.

`cargo test --release --locked --lib ksum` passed 8 of 8, including the
existing `ksum_wide_index_tests` (k up to 9).

No m = 6 or 7 arm beats ksum5 at any weight on either row.

## Why the predicted gain does not appear

The estimate `cost ~ sqrt(2 r (N+1))` counts only the final level of the
table. The build also pays one addition for every partial sum at every lower
level, `sum_{j=2..m} 2^(j-1) C(N, j)`. That includes partials that can never
be completed: a partial whose last abscissa leaves fewer than `m - j` later
abscissae still gets its addition. At these sizes N is only about 10, so the
lower levels are a large part of the build. For m = 6, N = 10 the build is
13.0k additions against 6.7k table entries. The recorded set-up GAE matches
this model to within 3 %. N is also coarse at these sizes: one step in N
changes the table by a factor of about 2 for m = 6, 7. So no N sits near the
continuous optimum.

The model `S = (build + (N+1) r / 2T) / sqrt(r)` predicts this ordering:

| row | m=5 best | m=6 best | m=7 best |
|:--|:--|:--|:--|
| B27, build as counted | 6.12-6.16 (N=11, 12) | 6.62 (N=10) | 7.76 (N=10) |
| B27, dead-end partials pruned | 5.78 (N=12) | 5.87 (N=10) | 5.85 (N=10) |
| P24, build as counted | 5.95 (N=11) | 6.64 (N=10) | 8.62 (N=10) |
| P24, dead-end partials pruned | 5.55 (N=11) | 5.57 (N=10) | 5.89 (N=10) |

Even with pruning, m = 6 and 7 at most tie m = 5 at 24-27 bits. They need a
larger r, where the optimal N is large enough that the lower levels and the
step size in N matter less.

## Recommendation

**No frozen m = 6/7 study at these sizes.** The threshold was at least 5 %
better at every weight. The best arm is 4-12 % *worse*, depending on row and
weight, and the model agrees.

There is a cheaper lever worth a separate, preregistered change. In
`KSumTable::extend`, stop the loop over abscissae at `len - (k - depth - 1)`
so dead-end partial sums are never computed. The model saves about 6 % of S
for ksum5 on both rows (B27 6.16 → 5.78; P24 5.95 → 5.55). This changes the
k <= 5 operation counts, so it must be a new flag (for example `prune=1`, off
by default) to keep the committed ksum4/5 sessions replay-identical. It needs
its own A/A-controlled study before any claim. Revisit m = 6/7 only at
r >= 2^30, or together with pruning.
