# Confirmation by a supplied-byte hash and exact file comparison

The private n47/m4 runtime control at85c1374 compiled but failed: the PDP witness was acknowledged, then the outer flush reported a persistence error. Its committed prefix contains one624-byte witness and no ordinary payloads. The original assertion did not print the exact error. Source inspection identifies final confirmation work admission as the likely cause; this remains a diagnosis to test. The complete failed logs and retained fixture are preserved in the S3 evidence receipt outside this source.

Confirmation previously hashed the supplied bytes against the committed identity, then hashed the file again. The updated confirmation still hashes supplied bytes and compares that digest/length with the committed receipt or registered payload. It then requires a regular file of the same length and compares every file byte against the already authenticated supplied bytes using the admitted4096-byte buffer. It checks EOF and the original deadline. Exact equality to bytes with the committed digest binds the same identity without a second hash. Initial publication retains its existing file-hash path.

The work quote changes from two witness hashes plus16n+8192 to one witness hash plus32n+8192. The32n covers read and byte comparison at16 per byte each. No remaining hash tariff, original total budget, checking partition, or deadline is reduced or enlarged. This is a resource-accounting implementation change, not an instruction-count or speedup claim.

The exact/one-unit-short confirmation control remains. Additional controls exercise624-byte and4102-byte valid JSON custody payloads, same-length changes at beginning/end/I/O boundary, truncation and extension. Failure must preserve the committed head and event count and make refusal sticky. The runtime control now writes its canonical artifacts before assertions, preserving terminal diagnostics if it fails again.
