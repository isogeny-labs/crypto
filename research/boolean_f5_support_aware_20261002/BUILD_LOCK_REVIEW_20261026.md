# Build-lock refresh — 2026-10-26

The working `Cargo.lock` was stale again. `tools/volcano-cli` (a path
dependency of the root `crypto` crate) declares `libc = "0.2"`, and the
`volcano-cli` entry in the lock did not list it, so every `--locked` build of
this study failed before any test ran: `error: cannot update the lock file
.../research/boolean_f5_support_aware_20261002/Cargo.lock because --locked was
passed to prevent this` (CI run 40251433848, job `correctness`, step
"Mathematical and native verifier tests").

The lock was regenerated by cargo (`cargo metadata --offline --manifest-path
Cargo.toml`), not edited by hand. The diff is one line, `+ "libc"` in the
`volcano-cli` dependency list. `libc` was already locked, so no package version
moved. `cargo metadata --locked` failed before and passes after.

Why this lock may be refreshed (checked, not assumed): nothing seals it. Its
SHA-256 appears nowhere on `main` (`git grep` over the whole tree, `research/`
included); there is no `FROZEN.json`, archive or verify script for this study;
`protocol.json` carries no lock hash; and no qualified run bundle has been
committed. `run.sh` copies the lock into each attempt's output directory, so a
future authorized run records the lock it used. The original lock stays
byte-for-byte in [`historical-locks/`](historical-locks/20261002-Cargo.lock),
as the [2026-10-19 review](BUILD_LOCK_REVIEW_20261019.md) arranged. The
protocol, worker and campaign sources are untouched.

This is a build repair. No discovery or holdout campaign was run, and no
historical measurement is reassigned to the new dependency set. The study's
test suite was not re-run for this refresh; CI's `correctness` job is the check.
