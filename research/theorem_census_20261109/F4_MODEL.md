# The original F4 model and saturation

The new Lean development imports the original `SubspaceCriterion.lean` and
`F4Containment.lean` byte for byte. Their shared `SolvingDegreeBound.lean`
dependency is also byte-identical to the existing project dependency.
`f4-model-imports.json` records those comparisons at copy time. Its historical
"not checked" compile field is not a later build verdict. [pcc:unverified]

For every field, variable type, degree bound and actual original `F4Run`, every
output belongs to the ideal generated by its original inputs. The proof uses
the original `run_subset`: the input ideal, restricted to a vector subspace,
is closed under variable multiplication. No assumption about C execution is
used. [pcc:unverified]

Saturation has a different domain. In every field, `y` belongs to
`(xy):x^∞`, with power witness 1, but not to `(xy)`. Evaluation at `(0,1)`
proves nonmembership. Lean directly negates the universal assertion that
every saturation member can appear in some ordinary `F4Run` from the same
generators. This refutes that unrestricted reading of the model, rather than
the ordinary algorithm's refinement claim. [pcc:unverified]

The zero-dimensional control uses

$$I=(xy,x^2-x,y^2-y),\qquad h=x.$$

Both `y` and `x-1` have power-1 saturation witnesses. Again, every input
vanishes at `(0,1)` and `y` does not. Therefore no actual original `F4Run`
from these generators can contain the registered saturated output rows.
The F101 module interprets printed coefficient 100 as actual -1, fixes the
expected ordinary and saturated rows, and proves this boundary for those
literal rows. These are proofs about polynomials, not a formal parser or
certificate of native execution. [pcc:unverified]
