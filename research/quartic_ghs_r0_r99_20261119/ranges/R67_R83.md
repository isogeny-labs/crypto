## Native deterministic screen

`r67_83.rs` deliberately uses a small many-to-one integer state machine, not
the elliptic-curve walk. This keeps the tested scheduler properties separate
from any claim about rho quality or performance. The executable checks:

- 6,000 job-bound worker/generation indices are pairwise distinct;
- 330 `(width,total)` tail cells across widths 1, 4, 8, 16, and 32 visit each
  active logical item exactly once;
- every worker uses the identical transition;
- a canonical key always routes to the same one of eight shards;
- the same run replays byte-for-value identically;
- a deterministic cross-walker DP collision is detected; and
- `total_steps = useful_steps + overshoot_steps`, with all six workers charged
  for all three simulated stop-delay rounds.

The final producer output was:

```text
R67-R83 deterministic invariant screen PASS
walker_indices_checked=6000
masked_tail_cells_checked=330
workers=6 shards=8 stop_delay_rounds=3
collision_round=10 collision_key=136 collision_shard=0
useful_steps=66 overshoot_steps=18 total_steps=84
distinguished_points=11 table_operations=11 occupied_keys=8 sterile_collisions=0
timing_observations=0 performance_claims=0
```

These are deterministic test values from the toy simulator
`[pcc:unverified]`. They do not establish that the production GHS walk has the
same values, or that any parallel implementation is faster.

## R67–R69: batch selection and tails

R67 retains the complete development grid:

- widths `1,4,8,16,32`;
- partition counts `16,32,64,128`;
- at least three sizes and three frozen seeds per size; and
- counted and counter-free counterparts with answer and authority checks.

No cell is eliminated from timing because its correctness/count result looks
expensive. Sequential elimination is allowed only at the preregistered stage:
full correctness/count screen, source-bound profile, host A/A, interleaved
ABAB development, then one primary and at most one sensitivity arm frozen for
holdout.

R68 makes partial lanes explicit. Production integration must add tests for
every tail length, retry mask, and terminal mask and run a memory sanitizer or
equivalent UB check. Scalar abstract-operation counts remain per active lane;
inactive vector slots are neither evaluated nor charged.

R69 may reorder physical storage only. It must carry the original lane id and
show that selected jumps, retry attempts, points, scalar coefficients, RNG
order, and every discarded attempt match the scalar lane oracle. The retained
Round C retry-compaction loss is evidence that fewer batch inversions alone is
not enough.

## R70–R74: data-parallel and memory layout

R70–R74 are conditional implementation leads, not automatic rewrites.

- R70 separates cubic coefficients across lanes behind a scalar oracle.
- R71 widens u32 products before reduction and refuses q outside the admitted
  `<2^31` domain.
- R72 records the selected kernel and observed host features. Unsupported
  features must select the scalar path before an architecture-specific
  instruction can execute.
- R73 separates point/coefficient/hash hot state from diagnostics and restart
  metadata only after a profile identifies load/store or cache pressure.
- R74 screens a frozen set of prefetch distances. It must never form an
  address outside allocated jump storage, including inactive tail lanes.

Vector instructions are diagnostic hardware counts. One vector instruction
must not be relabelled as one scalar field operation. Counted work continues
to report the scalar abstract operations, and a wall candidate must preserve
the complete counted counterpart.

## R75–R80: parallel distinguished-point mechanics

The production parallel design uses the same transition function and jump
table for every worker. Workers receive different deterministic trail-start
indices. Giving each worker a different walk would isolate collision domains
and invalidate the expected parallel collision search.

R75's DP record must retain enough data to check:

```text
R = a*P + b*Q
```

and to try both same-sign and opposite-sign collision equations when the
canonical key quotients by negation. Packing may reduce bytes; it may not
remove verification inputs or truncate coefficients.

R76 binds walker indices to the immutable job identity and worker count.
Production uses the repository PRF/conformance-vector convention rather than
the prototype's `mix64` diagnostic.

R77 binds the transition/jump identity into the job and every result. R78
routes one canonical DP key to one shard. R79 then adds bounded queues and a
ledger satisfying:

```text
submitted = processed + queued
processed = inserted + duplicate + sterile + collision + rejected
```

No queue-full path may discard a DP silently.

R80 records work through independently checked solution detection and stop
propagation:

```text
total_steps = useful_steps + overshoot_steps
```

The solution check, table probes, sterile collisions, queue work, and steps
performed during shutdown remain in the cold one-target record.

## R81–R83: measurement and portability contract

Every parallel run identity includes:

- source and binary hashes, compiler, target, and selected field kernel;
- worker count, CPU set, observed affinity, NUMA topology and memory policy;
- batch width, partition count, DP bits, queue capacity, shard count and
  table policy;
- job/curve/subgroup identity, seeds, trail-start derivation and stop policy;
  and
- setup, walk, DP-table, collision-check, and cleanup phase boundaries.

Mandatory reported observations are wall latency, total CPU seconds, total
and useful steps, overshoot, DPs, sterile and usable collisions, table
operations, queue waits, peak queue depth, peak RSS, and verification cost.
For a matched one-worker time `T1` and `p`-worker time `Tp`, the separately
labelled derived quantities are:

```text
latency speedup = T1 / Tp
parallel efficiency = T1 / (p * Tp)
```

They are computed only within the same admitted host class and frozen inputs.
Total work and CPU are reported beside latency, so a latency reduction cannot
be described as reduced expected rho work.

Cross-host measurements are never pooled directly. R83 first requires exact
scalar-fallback replay and per-host calibration, then reports host-specific
results. A SIMD result is bound to the feature-bearing host; it does not
replace the portable scalar baseline on unsupported hosts.
