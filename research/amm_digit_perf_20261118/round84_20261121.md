# Root-finding optimization Round84 (2026-11-21)

**Status:** experimental [draft PR #4875](https://github.com/isogeny-labs/crypto/pull/4875), based on [Round83 PR #4873](https://github.com/isogeny-labs/crypto/pull/4873). **Do not merge:** timings are mixed, the parent stack is unmerged, and there is no measured index-calculus relations/second improvement.

## Production Rust change

In `src/cryptanalysis/prime_root_trace.rs`, the independent root-certificate verifier previously held power and GCD replay states in two `HashMap<u64, ...>` tables. Power/GCD events use strictly consecutive computation IDs, so the new `Vec<Option<TraceComputation>>` holds both kinds in direct-indexed slots. It avoids hashing during PowerStep, PowerEnd, GcdStep and GcdEnd. It preserves wrong-type/repeated/missing ID rejection using `get_mut` and `Option::take` and checks all slots at Finish. No producer field arithmetic or event schema was changed.

New regression tests exercise complete root certificates and deliberately corrupt each of PowerStep, PowerEnd, GcdStep and GcdEnd IDs with `u64::MAX` across primes 17, 65,521, 1,000,000,007 and 2^61-1. Bad IDs must return a verifier error, not trigger large allocation. Existing certificate, tampering, sink-failure and work-limit tests are included.

## Native Rust A/B results

[Successful source-exact Rust CI, raw CSV artifacts](https://github.com/isogeny-labs/crypto/actions/runs/44890179039). Rust 1.100.0 release, 15 alternating before/after trials per workload, three primes, constructed degree-one, -two, -four and -eight inputs. CPU pinned to one GitHub-hosted logical CPU. Output checksums and completion matched across **450 paired case/trial comparisons**. The production Rust producer and verifier files were compiled in isolated crates; unrelated bounded API and primality admission were stubbed for known prime inputs. These are not full-repository integration results.

Medians below are nanoseconds per **complete solve + verify**. Speedup is before/after, >1 faster.

## Round83 four-variant ablation

The same passing workflow compiled four whole-source Rust variants: Round82 baseline, event-check-only change, degree-eight-factor-only change, and Round83 combined. Nine rotating-order trials, three primes, quadratic/quartic/degree-eight cases with verify-only controls; **648 checksum-matched variant/case/trial results**. Most isolated event-only full solve+verify speedups were about **1.00x–1.01x**, often within noise. The degree-eight factor reconstruction registered 1.1478x for 61-bit degree-eight in this particular sample but was near 1.01x for 32-bit degree-eight, while 32-bit quadratic/quartic regressed to 0.9672x/0.9823x in the factor-only source. These vary materially from some earlier Round83 results. Source and raw CSV: [round84_ablation.py](round84_ablation.py), uploaded by the CI workflow. Do not use them to justify merge until repeated on isolated hardware with controlled frequency/thermal conditions.

## Local CPU-pinned kernel reproduction

On the local runner, GCC 14.2 and Clang 17 compiled a **C++ model of the hash-versus-indexed state lookup** with 13 alternating paired trials and correctness checks. For four live computations and 32 state updates per computation, GCC measured **1.584x** and Clang **1.581x** isolated speedup. For 16 live computations and 4 updates, GCC measured **2.591x** and Clang **2.485x**. The source/CSV/UBSan/perf diagnostics are archived in `rootfind-round84-20261121.zip` in the conversation attachment. UBSan and consistency tests passed.

**These isolated C++ analogues are not native Rust full-solver improvements.**

## `perf` limitation

Local `perf` executable is unavailable. `perf_event_open` probes for task-clock and cycles returned `EACCES`; `/proc/sys/kernel/perf_event_paranoid` was 2. We cannot report hardware PMU counters for this run. Wall-clock/steady-clock medians were used with fixed CPU affinity. No fabricated instructions, cache misses, or cycle counts.
