# Round 56: monomial x^d polynomial rootfinder kernels

**Date:** 2026-11-20 UTC  
**Production file:** `src/cryptanalysis/prime_root_bounded.rs`  
**Branch/PR:** `automation/amm-cuberoot-digits-20261118`, [PR #4706](https://github.com/isogeny-labs/crypto/pull/4706)

## Implementation

The polynomial ring identity `f(x) mod x^d = sum_{i=0}^{d-1} f_i x^i` permits direct truncation. Also `f(x) = x^d * floor(f/x^d) + (f mod x^d)`, with the quotient just the shifted high-coefficient sequence. Four production paths now specialize monic powers `x^d` for `d >= 2`:

1. `Producer::division`: split the high and low coefficient arrays directly.
2. `Producer::reduce_monic`: truncate high coefficients.
3. `Replay::remainder`: independently truncate the low coefficients, including any nonzero leading scalar on the divisor.
4. `Replay::cancel_monic`: independent truncation with replay-specific work accounting.

For producer division/reduction the metered work counts nonzero high-degree cancellations, consistent with the former trim-driven method. For replay the original fixed descending traversal checked every degree, so the fast path aggregates the same number of COPY_WORK charges. All four preserve deadline/budget checks, no field arithmetic is needed, and all outputs remain canonical Poly17 values.

A new unit test compares against an independent coefficient-split oracle across 4 primes, degrees 2 through 8, multiple input lengths, and 32 randomized polynomials per length. The source-exact paired Rust CI tests both the original and modified source using R56 markers.

## Local benchmark: CPU-pinned C++ arithmetic reproductions

These numbers are **not Rust production performance**. AMD EPYC 9V74, pinned CPU 0, GCC 14.2 and Clang 17 at -O2, 13 alternating A/B trials, 128 input polynomials times 12 repetitions per trial, median wall-clock nanoseconds per call. The reproductions include monotonic-clock accounting on budget checks. Each case passed before/after equivalence; GCC UBSan passed.

| p | Degree of modulus | Kernel | GCC before → after | GCC speedup | Clang speedup |
|---|---:|---|---:|---:|---:|
| 1,000,000,007 | 8 | Producer division | 223.53 → 50.68 ns | **4.41×** | 4.72× |
| 1,000,000,007 | 8 | Producer reduction | 268.08 → 44.23 ns | **6.06×** | 4.54× |
| 1,000,000,007 | 8 | Replay cancellation | 228.83 → 44.18 ns | **5.18×** | 4.28× |
| 1,000,000,007 | 8 | Replay remainder | 211.45 → 44.08 ns | **4.80×** | 4.37× |
| 2^61−1 | 8 | Producer division | 255.99 → 50.75 ns | **5.04×** | 4.27× |
| 2^61−1 | 8 | Producer reduction | 234.88 → 44.21 ns | **5.31×** | 4.24× |
| 2^61−1 | 8 | Replay cancellation | 213.28 → 44.22 ns | **4.82×** | 4.28× |

Lower-degree moduli (`x^3`, `x^4`) typically improved by roughly 2–3×. A more general `x^d+c` binomial reduction candidate was screened but showed inconsistent results and regressions on some configurations, so it was **not** deployed.

## Perf and remaining validation

Linux `perf` executable was missing in the available local runtime. Direct `perf_event_open` probes returned `EACCES` for `task-clock`, `cycles` and `instructions` (kernel `perf_event_paranoid=2`). This report therefore **does not claim hardware PMU measurements**; it reports pinned wall-clock timings and instruction-level algebraic operation savings only.

The new [dedicated source-exact native Rust CI](https://github.com/isogeny-labs/crypto/actions/workflows/radical-root-arithmetic.yml) compiles the production Rust source twice, with and without only the four R56 sections. It checks independent coefficient oracles, exact before/after outputs and runs 13 alternating production-Rust paired timing trials. CI results must be checked at the final commit before a Rust speedup is asserted.

**Limits:** This isolates `x^d` arithmetic, which is a special-case divisor; no degree-8 whole-rootfinding or index-calculus relations-per-second improvement has been established for this round. The previous rounds' broader runtime improvements must not be confused with these isolated kernels.
