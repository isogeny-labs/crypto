# Round 39 (2026-11-19): omit identity powering and monic linear inversions

**Production**: `src/cryptanalysis/prime_root_bounded.rs`, [PR #4706](https://github.com/isogeny-labs/crypto/pull/4706).

Four optimizations (plus a measured regression guard):
1. Producer polynomial power assigns the already reduced base for its first set exponent bit, omitting `1 * b mod m`, and skips reduction of the identity for positive-degree moduli.
2. Independent replay power initializes the accumulator from the reduced base for nonzero exponents, avoiding the first square of 1 and multiply by the base. Zero exponent and degree-zero modulus are handled explicitly.
3. Producer linear-root extraction uses `root = -c` when the linear polynomial is monic, avoiding Fermat inversion and multiplication.
4. Independent replay verifies monic linear roots with `root + c == 0`, retaining its generic multiplication path for nonmonic inputs.

For exponents larger than u32::MAX, the producer and replay retain their previous algorithms because local screening showed mixed or regressed timings. This guard avoids a speculative high-bit shortcut on 61-bit prime workloads. These are public-input, variable-time specializations, **not** constant-time cryptographic code.

## Local profiling: limits and negative controls

AMD EPYC 9V74, GCC 14.2 and Clang 17, pinned CPU 0, `-O3`, nine alternating before/after trials. Local standalone C++ arithmetic reproductions (not Rust) passed **2,688 equality checks per compiler**, including GCC UBSan. Monic linear-root microkernels improved **15.91x / 49.49x / 127.49x** for p=487 / 1e9+7 / 2^61−1 under GCC; Clang showed **16.08x / 47.82x / 126.95x**. These speedups **do not** apply to whole-root throughput. Nonmonic controls were approximately neutral. The earlier unguarded polynomial-power reproduction had mixed results and some regressions (GCC producer Frobenius 0.92–1.02x); the >32-bit guard was added and independently tested in Rust. These complete-Rust timings remain the primary retention evidence.

The `perf` executable is **not installed** locally, and `perf_event_open` returned **EACCES** for both software task-clock and hardware cycles (`perf_event_paranoid=2`). Consequently local results are wall-clock only; no hardware PMU statistics or cycle-count claims are made.
