# Round 126: optimized small-leading linear roots (2026-11-22 PT)

## Candidate selection

Target: `src/cryptanalysis/prime_radical_root.rs`, public prime-field radical root finding.

1. **Retained experimentally:** reuse the context's precomputed `inv3` and `inv4` when solving linear `a x+b=0`, restricted to `p>=2^20`. The full context already computes these inverses for Cardano/Ferrari; no new setup work is introduced.
2. **Rejected after native Rust:** replace `inv(2)` multiplication by direct `Fp::half`. It improved isolated C++ but was near parity or slower in whole Rust linear-root queries.
3. **Rejected:** replace `inv(2a)` in general quadratics by a cached `inv(a)/2` for `a=2,3,4`. Full quadratic throughput was noisy or negative, particularly random discriminants.
4. **Compiler fix:** remove an unused `Fp::reciprocal32` struct field declaration that had no corresponding initializer; `reciprocal_64` remains the operative field.

All paths operate on public polynomial coefficients, not secrets. Unrestricted leading coefficients continue using the original Euclidean inverse.

## Local Linux perf screening

AMD EPYC 9V74, pinned CPU 0, GCC 14.2 and Clang 17 `-O3`, two independent executions of 13 alternating before/after trials per compiler. `perf_event_open(PERF_COUNT_SW_TASK_CLOCK)` succeeded. The `perf` CLI / hardware counters were not available.

The isolated C++ source-aligned linear-root reproduction for `p=1,000,000,007` measured:

| Case | GCC before -> after ns/query | GCC speedup | Clang speedup |
|:---|---:|---:|---:|
| Leading `a=3` | 5.44 -> 2.72 | 2.00x | 1.98x |
| Leading `a=4` | 5.43 -> 2.72 | 2.00x | 1.81x |
| Leading `a=2` control | 2.72 -> 3.53 | 0.77x | regression |
| Random leading control | varies with Euclid | mixed | mixed |

These C++ results are **not** the production Rust speedup. They screen arithmetic paths only, using independently verified exact modular products. Each C++ execution passed 49,152 A/B linear and quadratic comparisons and 300,000 independent modular product checks. GCC ASan/UBSan passed. Raw trial CSVs and the C++ harness are provided separately with this run.

## Final measurement audit and merge correction, November 22 PT / November 23 UTC

**This section supersedes the preliminary single-run acceptance and merge-status language above.** PR [#4944](https://github.com/isogeny-labs/crypto/pull/4944) was **merged** at 03:36:17 UTC on November 23, before all repository CI was green, while additional measurements were still finishing. The source revision is a working experiment rather than a validated global performance improvement.

The retained source-exact native Rust A/B branch had three completed runs. Each passed **30,720** equivalence comparisons and 13 alternating A/B timing trials. **Reproducibility:** the large 61-bit-prime improvement holds in all three runs. The 32-bit prime improvement does *not* reproduce in Run C, and random leading coefficients regress in several runs. These results do not establish a net root-finder throughput gain. The source-exact benchmark uses the actual Rust root code, but substitutes unused tracing dependencies rather than compiling the whole repository.

Fresh independently repeated local Linux task-clock performance screening (AMD EPYC 9V74, pinned CPU 0, GCC 14.2 / Clang 17, two runs of 13 alternating A/B trials) measured isolated `a=3` and `a=4` arithmetic improvements of approximately 1.95–2.65x under GCC and 2.01–2.65x under Clang. For `p=1e9+7`, GCC's `a=3` case was **5.314 -> 2.722 ns/query (1.952x)**; Clang's `a=4` case was **5.428 -> 2.183 ns/query (2.487x)**. These are **C++ algorithmic reproductions**, not production Rust measurements. Random-leading controls varied and sometimes regressed.

The broad repository CI still contains failing older frozen baseline harnesses and `prime_root_trace.rs` syntax issues; merge should not be interpreted as clearing those gates. Required follow-up: fix the independent compilation errors, analyze compiler-layout/timing instability, run longer native A/B measurements under representative mixed distributions, and measure true relation throughput. No ECC2K relation-finding speedup has been demonstrated.
