## Source change

After the canonical `u32` Jacobi prefilter establishes that a discriminant is a quadratic residue in `F_p`, `p=4,294,967,291 = 2^32-5`, dispatch the already-existing exact `sqrt_power_4294967291(a)` chain rather than re-entering generic `Fp::powm`.

For this prime, `(p+1)/4 = 2^30-1`. The fixed chain uses 29 squarings and 6 coefficient multiplications versus approximately 29 squarings and 30 multiplications in the generic binary path, saving 24 multiplications on positive Jacobi discriminants. The Jacobi sign and noncanonical fallback are preserved. No new exponent formula or variable-time secret-key operation was introduced.

A source-exact Rust correctness and paired timing workflow has been added as `.github/workflows/radical-root-round119.yml`, with the frozen prior implementation reconstructed from source in `research/amm_digit_perf_20261118/round119_discriminant_chain_ab.py`. Its outcome must be checked before accepting a production Rust speedup.

## Investigated candidates

1. Reuse the existing addition chain in `sqrt_discriminant` after canonical 32-bit Jacobi: **retained for source-exact CI evaluation**.
2. Early return for discriminants 0 and 1: **rejected as a blanket change**, despite enormous constant-input speedups, because local uniformly random GCC performance regressed to 0.862x.
3. Early return in standalone square root for 0 and 1: **not retained** pending native Rust end-to-end distribution and performance checks. This changes uncommon special inputs but adds a branch to every nonzero sqrt.
4. End-to-end quadratic path through `quad_monic`: benchmarked separately to detect swallowed arithmetic wins; no separate code modification.

## Local hardware and measurement

AMD EPYC 9V74, CPU 0 affinity, GCC 14.2 and Clang 17, `-O3 -std=c++17`, each benchmark repeated in two independent executions with 15 alternating before/after trials and 32,768 evaluations per trial. Linux `perf_event_open` successfully captured `PERF_COUNT_SW_TASK_CLOCK` (software task-clock). Hardware PMU cycles, instructions, cache misses, and the `perf` CLI were unavailable. Timings are median software task-clock nanoseconds per operation.

These are **C++ reproductions of the arithmetic/control flow, not production source-exact Rust**. They are a candidate screening signal, not a sufficient merge gate.

| Workload (p=2^32-5) | GCC run 1 | GCC run 2 | Clang run 1 | Clang run 2 |
|---|---:|---:|---:|---:|
| Uniform discriminant, chain vs generic power | 1.033x | 1.018x | 0.964x | 0.995x |
| Known-square discriminant, chain vs generic power | 1.139x | 1.095x | 1.084x | 1.040x |
| Full monic quadratic with uniform coefficients | 1.046x | 1.042x | 0.982x | 1.023x |
| Full monic quadratic with known roots | 1.075x | 1.080x | 1.128x | 1.031x |
| Canonical unit-discriminant early return, isolated | 81.45x | measured | 86.15x | measured |
| Uniform discriminant early return after chain | 0.862x | measured | 0.984x | measured |

The extraordinary unit-input ratios are workload-specific to a constant case and **must not** be presented as overall speedups. The randomized Clang control sometimes regressed; this is why native Rust acceptance remains mandatory.

Local C++ test compared before/after arithmetic for 200,011 inputs per compiler, including 200,000 randomized combinations of discriminants and monic quadratic coefficients; all matched. GCC ASan/UBSan passed.
