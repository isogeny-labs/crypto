# Round 127: small leading-coefficient inverse table

**Date:** 2026-11-23 UTC. **Status:** experimental, not merge-ready.

## Target and source changes

- `src/cryptanalysis/prime_radical_root.rs`: initialize an 8-element per-prime inverse table. Existing Cardano/Ferrari inverse constants 2, 3, 4 are reused; 5, 6, 7 are precomputed at context creation.
- `RadicalRootCtx::roots`: for canonical linear leading coefficient 3..=7 at p >= 2^20, index the table rather than execute extended Euclid. Leading coefficient 2 retains the existing behavior based on negative prior native tests.
- `inv_leading`: reuse the same table for zero-constant quadratics and other already-covered call sites.
- Added correctness regression tests covering p=5,7,65,521,1,000,000,007,4,294,967,291,2^61-1, coefficients 2..=7, linear and zero-constant quadratic equations.

## Local profiling

Intel Xeon Platinum 8573C, GCC and Clang, -O3 -march=native, CPU 0 pinned, Linux perf_event_open software task-clock. Two independent executions per compiler; 13 alternating A/B pairs per test. 2,048 canonical public queries per batch, 20 repetitions per trial. Before=existing inv3/inv4 matches followed by Euclid, after=one guarded 0..7 table lookup. C++ arithmetic reproduction only, **not a source-exact Rust benchmark**.

| Workload | GCC speedup (run 1 / run 2) | Clang speedup (run 1 / run 2) |
|:--|--:|--:|
| p=1e9+7, a=5, linear | 2.340x / 2.568x | 2.557x / 2.564x |
| p=1e9+7, a=7, linear | 2.277x / 2.503x | 2.582x / 2.764x |
| p=2^32-5, a=5, linear | 2.079x / 1.897x | 1.958x / 2.011x |
| p=2^32-5, a=7, linear | 2.440x / 2.401x | 2.432x / 2.417x |
| p=2^61-1, a=5, linear | 1.668x / 2.079x | 2.245x / 2.522x |
| p=2^61-1, a=7, linear | 2.170x / 2.299x | 3.033x / 1.700x |

Zero-constant quadratic isolated reproductions yielded similar coefficient-specific gains (~1.8-2.6x in first runs). Random-leading coefficient controls were noisy and **sometimes regressed by 6-8%**, so no aggregate speedup is claimed. The table also adds three context-init inversions, which were not included in steady-state per-query timing. This matters if each context handles few queries.

## Rejected optimization

For quadratic-extension Fp² arithmetic, replacing multiplication by a nonresidue n=5 or 7 with repeated modular additions was mathematically correct (3.6 million field comparisons and 3,072 powering comparisons), but slowed multiplication, squaring, or cubing in GCC/Clang screening. Do not merge this candidate.

## Correctness and limitations

- Local GCC and Clang arithmetic screening passed 49,152 before/after linear and zero-constant quadratic comparisons per execution; GCC ASan/UBSan completed without findings.
- Hardware cycles/instructions/cache misses were unavailable. Software task-clock counters succeeded.
- **No native Rust performance result** was obtained in this environment (Rust toolchain absent and network git clone unavailable).
- The current repository's `prime_root_trace.rs` contains existing malformed Rust syntax (e.g. incomplete `monic_power_degree`) and broken test fragments; broader `cargo test` must be repaired before this can be accepted. The present PR does not try to repair unrelated baseline corruption.
- No end-to-end ECC2K index-calculus relations/sec result exists.
