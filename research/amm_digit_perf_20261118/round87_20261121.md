# Round87: quotient-free remainder replay for prime root certificates

Date: 2026-11-21. [Draft PR #4878](https://github.com/isogeny-labs/crypto/pull/4878). Based on the known passing Round82 source (`359e1140f5315feac52e116bd5ea96ab49b22389`).

## Code and correctness

Optimized `src/cryptanalysis/prime_root_trace.rs` in the independent verifier, not the trace producer:

1. `vremainder` performs fixed-degree reduction of a polynomial by a dense monic modulus without allocating or trimming the quotient. The constant and highest-term field arithmetic remains unchanged. Existing `vdiv` handles sparse/binomial, nonmonic, and short moduli.
2. Four modular-reduction call sites in `vpower` now select remainder-only reduction instead of the quotient-and-remainder path.
3. Euclidean remainder replay inside `vgcd` also uses the same remainder-only dispatch.
4. Inlining the dispatcher reduces, but does not eliminate, the sparse fallback overhead.

The independently checked Division trace events still use the original `vdiv` and verify both quotient and remainder. The producer and certificate format are untouched. The new Rust reference test compares 6,240 quotient/remainder-equivalent generated examples across 3, 5, 65521, 1000000007 and 2^61-1, degrees 3–8. The independent Python reference also passed 6,240 corresponding examples.

## Native Rust source-exact measurements

[First passing run](https://github.com/isogeny-labs/crypto/actions/runs/44904562624), 450 paired comparisons. [Second passing run](https://github.com/isogeny-labs/crypto/actions/runs/44904766347), 720 paired comparisons. [Third passing run](https://github.com/isogeny-labs/crypto/actions/runs/44904911784), 720 paired comparisons, after inlining. Rust 1.100.0, optimized release, 15 alternating A/B trials per case with CPU affinity pinned. Outputs and completion statuses match; targeted regression tests pass.

Representative third-run median operations (ns):

| Field | Workload | Before | After | Speedup |
|---|---|---:|---:|---:|
| p=65521 | dense monic degree 3 remainder kernel | 54.423 | 39.865 | **1.365x** |
| p=1e9+7 | dense monic degree 3 remainder kernel | 55.662 | 42.040 | **1.324x** |
| p=2^61−1 | dense monic degree 3 remainder kernel | 52.596 | 38.380 | **1.370x** |
| p=2^61−1 | dense monic degree 4 remainder kernel | 61.326 | 52.187 | **1.175x** |
| p=2^61−1 | verifier-only quartic | 191396.656 | 183226.062 | **1.045x** |
| p=2^61−1 | complete quartic solve+verify | 446232.977 | 425076.453 | **1.050x** |
| p=65521 | sparse degree 8 remainder kernel | 61.061 | 67.547 | **0.904x** |
| p=2^61−1 | dense degree 8 remainder kernel | 137.807 | 146.763 | **0.939x** |
| p=65521 | complete degree 8 solve+verify | 599120.500 | 761028.875 | **0.787x** |
| p=1e9+7 | complete degree 8 solve+verify | 1570171.000 | 1248732.875 | **1.257x** |

The p=65521 degree-eight complete-solver regression was present across three independently passing runs (0.750x, 0.733x, 0.787x), while verifier-only octet performance was near parity to +3.4%. Conversely p=1e9+7 degree eight improves ~25% at full-solver level while verifier-only is essentially unchanged. Since the producer source did not change, these large opposite-direction shifts may reflect compiler code-layout/inlining effects or uncontrolled benchmarking variance. Do **not** attribute them to quotient-free verifier arithmetic without an ablation/profile.

Sparse fallback overhead remains measurable (~4–10% regression with inlining), which is a reason to restrict call-site dispatch or remove this shortcut from those paths before acceptance. Smaller workloads have mixed results.

## Local GCC/Clang screening

On a CPU-pinned AMD EPYC 9V74, 13 alternating C++20 `-O3 -march=native` before/after trials per case, the quotient-free analogue is generally faster on dense small-degree reductions. Example p=1e9+7 degree-2 analogue: GCC 31.10→22.07 ns (1.41x), Clang 32.34→22.06 ns (1.47x). General degree-8 dense analogues are near parity, and some regress. GCC UBSan passed. These C++ analogues do **not** establish native Rust performance.

`perf` could not run locally: executable missing and direct `perf_event_open` for cycles and task-clock returns EACCES (`kernel.perf_event_paranoid=2`). All metrics use paired wall-clock sampling, not CPU hardware counters. Local raw benchmark CSV and reproducible test sources are included in the run's attached ZIP.

## Decision and next gates

Remain **draft, unmerged**. Dense low-degree kernel reductions are real, but complete-solver results are not reliably better. Restrict optimized dispatch away from sparse/degree-eight cases, isolate producer-only and verifier-only timing under stable code layout, repeat on a perf-enabled host, run repository-wide tests, and measure actual index-calculus relations per second. No relations/sec benefit has been demonstrated.
