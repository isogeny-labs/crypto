## 2. n = 131 arithmetic and curve constants

Own code: bit-serial shift-and-reduce multiply on `[u64; 3]`, inversion as the product of
a^(2^i), i = 1..130, own half-trace lift and affine addition; independent of `mw.rs`.

- z^131 + z^8 + z^3 + z^2 + 1: x^(2^131) = x on 12 of 12 random x, f(0) = f(1) = 1, 131 prime:
  irreducible. Control z^131 + z^8 + z^3 + z + 1: 0 of 12 (the test can fail).
- `mw.rs` against mine: multiply 0 of 20,000 differ, square 0 of 20,000, inverse 0 of 2,000.
- 600 liftable of 1,204 random abscissae: liftability and y agree with `mw.rs`; all on
  y^2 + xy = x^3 + 1. 300 random pairs: addition and doubling equal to `mw.rs`, sums on the
  curve, S3(x(P), x(Q), x(P+Q)) = 0 on all (symmetric form (e2)^2 + e3 + 1) and nonzero on an
  unrelated third abscissa, associativity holds on 300 triples.
- Curve: ECC2K-130 is y^2 + xy = x^3 + 1 (a = 0, b = 1):
  `src/cryptanalysis/ecc2k130_guard.rs:851` ("certicom-ecc2k-130: y^2 + xy = x^3 + 1 over
  GF(2^131)") and `ecc2k130/codegen/curves.py:390` (`CurvePb`). Correct.
- **Modulus: the pilot's polynomial is not the challenge's published one.**
  `src/cryptanalysis/ecc2k130_guard.rs:852` and `docs/curves/ICV1.md:95` give
  x^131 + x^13 + x^2 + x + 1. The pilot uses z^131 + z^8 + z^3 + z^2 + 1, which is `f_1` of
  `ecc2k130/benchmarks/sparse-basis-compound/PROTOCOL.md:23`, an alternative representation
  studied for hardware reduction. The fields are isomorphic and the curve is the same, but the
  factor base "degree < d in the polynomial basis" is a different set of points: I get
  A = 10, 17, 34, 74, 131, 252 at d = 4..9 for the pilot's modulus (the panel's values, so the
  panel `research/notes/ecc2k130/RESEARCH_ECC2K130_RR_SOLVER_PANEL.md` section 11 used the same
  one) and A = 7, 14, 33, 63, 126, 249 for the Certicom modulus. The pilot matches the panel; it
  should say "ECC2K-130 curve in the f_1 representation", not imply the published basis.

## 3. Ground truth at n = 131

- Brute force with my own arithmetic (all unordered pairs of base points, third point looked up
  in a hash set), on the producer's measured targets at d = 6, 7 and 8: 24 uniform targets, all
  non-decomposable; 6 planted targets, all decomposable. Equal to the solver, fast-leaf and pair
  verdicts in `raw/rows_k130.jsonl`. d = 9..14 not ground-truthed by me (cost of my slow field):
  there the only reference is the producer's own two arms. Weaker than stated to that extent.
- All 36 planted solver models (d = 6..14) lift with my code and have a signed sum with
  abscissa x_R: 36 of 36.
- Factor base, exactly: `mw.rs` builds all rational points with nonzero abscissa of degree < d,
  both signs (2A points), **plus the 2-torsion point T = (0, 1)** (`points[0]`). A, as the panel
  defines it, counts nonzero abscissae only; C(A, 2) therefore does not count pairs with T, and
  `pairs` tests (2A + 1)(2A + 2) / 2 point pairs.
- The encoding excludes x1 = 0 (the gate chain is contradictory there) but allows x2 = 0 or
  x3 = 0, so the solver too decides "R = +-P1 +- P2 +- P3 with P1 in the base and P2, P3 in the
  base or equal to T". Tested on 30 constructed targets at d = 6 (3 repetitions of 10 classes),
  my brute force with and without T against the three arms:

  | target class | without T | with T | solver / fastleaf / pairs |
  |---|---|---|---|
  | P1 + P2 + T | not decomposable | decomposable | SAT (model lifts, x = 0 used) |
  | P1 + U, P1 + U + T (U = (1, 0), order 4, 2U = T) | not decomposable | decomposable | SAT |
  | P1 + T | decomposable (P1 + U + U; x = 1 is in V and lifts) | same | SAT |
  | 2 P1 + P2, 3 P1, P1 + P2 + U | decomposable | same | SAT |
  | P1 + P2, 2 P1, (random point) + T | not decomposable | same | UNSAT |

  So the three arms agree with each other on every class and decide the problem **with T in the
  base**; on the classes P1 + P2 + T and P1 + U they answer SAT where the panel's base
  (nonzero abscissae) gives no decomposition. About (2A)^2 targets out of 2^131: none of the 90
  measured targets is affected, and no measured number changes. It is a definitional gap between
  the verdict and the unit C(A, 2), not disclosed.
- Cofactor 4: the earlier pilot's admission rule (exclude sqrt(b) / x_R in V, where a = 1 gives
  non-liftable twist models) is not applied at n = 131 (`gen_targets`). On this curve it is not
  needed: the only non-generic solutions of S3(0, x2, x3) = 0 in V are x2 = x3 = 1, which lifts
  (the order-4 point), and the P1 + T rows above return liftable models. "Non-decomposable" for
  the uniform targets means: a random rational abscissa outside V, **assumed** non-decomposable
  and confirmed only by the arms' own UNSAT (and by my brute force at d = 6..8). At these sizes
  the chance of a decomposable uniform target is below 2^-80, so the label is right.

## 4. Deletion and the learning-free leaf

Code reading (`fastcdcl_mw.rs`): the flip asserts the negation of the topmost decision with a
reason that analysis expands to the negated lower decisions; that clause is implied whenever a
conflict is reached under those decisions, whatever learnt clauses exist, so the rule is sound,
and the search stays complete (chronological). `locked` protects a clause that is the reason of
an assigned literal; reasons are reset on backtrack, so a reused slot cannot be referenced by a
stale reason. I found no defect.

**Gap in the producer's evidence:** in arm `delleaf` (keep 64) `deleted_clauses` is 0 in every
one of the 2,800 differential instances and every one of the 176 measured targets (the leaf rule
leaves at most 64 learnt clauses). `delleaf` behaved as `leaf`; deletion together with the flip,
and deletion of clauses that had been reasons, were not exercised. `del` alone did delete (up to
12,275 clauses per target at l = 13).

My differential test (`dt2.rs`: the harness with added arms keep-0, keep-0 + leaf, keep-1 + leaf,
keep-2 + leaf, new cells and a switch that removes priority variables in both solvers so that
real learning, locked clauses and flips mix; reference: the unmodified `fastcdcl.rs` and the
pair oracle of `base_lin21_verbatim.rs`, which are the earlier pilot's code, not mine):

| run | cells (n, l) | instances | arms | verdict mismatches | bad / non-liftable models | flips, deletions in keep-1 + leaf |
|---|---|---|---|---|---|---|
| seed 4410077, priority as shipped | (11,3) (13,3) (14,4) (16,4) (17,5) (19,5) (20,6) (23,7) | 3,200 | 9 | 0 | 0 of 14,670 | 107,155 / 104 |
| seed 5520081, last 2 priority bits removed | same | 3,200 | 9 | 0 | 0 of 14,724 | 62,459 / 39,745 |
| seed 6630083, no priority variables | same | 2,000 | 9 | 0 | 0 of 9,207 | 4,988 / 58,369 |

8,400 fresh instances (about half decomposable), 75,600 arm runs, 0 verdict differences from the
unmodified solver or the oracle. Conflict counts: `mw` (W = 1) and the two-word control equal to
the unmodified solver on 8,400 of 8,400; the deletion-only arms (keep 64, 1, 0) on 8,400 of
8,400; the five leaf arms differ on 3 instances (all at (20, 6)), by one conflict where a sum is
visible. Deleting every unlocked learnt clause at once never changed a conflict count: learnt
clauses do not prune this search, they only cost propagation time. That is the content of
claim B's mechanism.

## 5. Fairness of the ECC2K-130 comparisons

- **Conflict count.** Every uniform row has exactly 2^d + A conflicts (98, 202, 387, 764, 1543,
  3071, 6098, 12329, 24559; the 8 targets of a cell are identical, so the "median" is a
  constant): one conflict per x1 in V, one more per liftable x1, one final. That is 1.5 per x1
  value, the same as the balanced series' 1.5 * 2^l; "about 3 A" is the same count in a unit
  that is half as large (A is about 2^d / 2). Over-determination does not double anything. It is
  the 2+1 enumeration count, fixed by the priority order, with zero pruning.
- **"0.0455 x C(A, 2) against CryptoMiniSat's 36.7".** Compares a linear count with a quadratic
  unit. In the same unit the fast scan uses 2A + 1 leaves = 0.031 x C(A, 2) at d = 8, fewer
  than the solver's conflicts. The README says the comparison says nothing about wall time; it
  should also say the scan's own count is lower.
- **Pair enumeration.** It is a reasonable but untuned implementation. Measured 303 to 334 ns
  per point pair; `mw.rs` costs 22 ns per multiply and 13 ns per square at n = 131 (my timing,
  20 million dependent operations), so the arithmetic of one pair (3 multiplies of batch
  inversion, 1 multiply, 1 square) is about 100 ns. P and -P share a denominator that is
  inverted twice, and it enumerates point pairs (about 4 C(A, 2)), which is how the abscissa
  pairs must be covered. A tight loop would be about 3 times faster (estimate, not measured);
  the crossing with the solver would then be near d = 12.5 instead of d = 11, and "0.52x at
  d = 12" would be about 1.5x. The crossing itself is real: pairs grow 4x per d and the solver
  2x. It has no decision value: nobody would use pair enumeration when the scan exists.
- **Fast scan.** Confirmed as the baseline for any decision here: 0.335 / 6.45 / 30.4 ms against
  78.7 / 1,268 / 5,779 ms, 187 to 271 times faster than the solver at every d, with no trend
  toward parity (solver slope +1.00 per d, scan +1.06: the scan's per-leaf time rose from 1.2 to
  1.9 microseconds, most likely cache, not the algorithm). The solver's field arithmetic is
  bit-serial and it inserts 131-row gates before the contradiction; both are implementation
  choices, so the 190x is an upper bound on this code, not a property of the method.
- **Transfer to the balanced regime.** None. At n = 131 and d <= 14 a leaf has 3d - 1 <= 41
  unknowns and 131 equations: 0 consistent leaves, 0 learnt clauses, no kernel enumeration, no
  root split. Index calculus with m = 3 on this curve needs d about 43 or 44, where about one
  leaf in 8 is consistent and the scan alone is about 2^44 leaves per target. Nothing measured
  here bears on that; the only balanced data are the small-field series, n <= 41.
- **"One target at d = 14".** Disclosed in the tables.md row ("1 targets"), the README table and
  deviation 3. Not disclosed in the README's lead paragraph ("0.14 at d = 14"), in the slope of
  `pairs` (+1.88, which includes that cell) or in `fig_k130_wall.svg`. The ratio 0.138 divides a
  median over 8 targets by one run.

## Problems

1. `delleaf` never deleted a clause in any producer run; the claim "verdict-identical with
   deletion and the learning-free leaf" was untested for the combination. Closed by my 8,400
   instances, which reuse the earlier pilot's oracle (not an independent one).
2. The modulus is `f_1` of the sparse-basis benchmark, not the challenge's published
   x^131 + x^13 + x^2 + x + 1; the factor base differs between the two (A differs). Say so.
3. The base contains the 2-torsion point while A and C(A, 2) do not; targets P1 + P2 + T and
   P1 + U are SAT for all three arms and not decomposable over the panel's base. Not disclosed;
   no measured row affected.
4. "2.88 to 3.05 x A conflicts" is exactly 2^d + A, the scan's enumeration with no pruning; the
   comparison with CryptoMiniSat's 36.7 x C(A, 2) flatters by unit. The fast scan's own count is
   lower.
5. "0.52x of pair enumeration at d = 12" is against a loop about 3x slower than its arithmetic;
   and the comparison is irrelevant next to the scan (190x faster than the solver).
6. Slope "flat" rests on two cells (l = 9 and 13, 6 targets at l = 13); the threshold is inside
   the noise of one median.
7. d = 14 single pair run not flagged in the lead paragraph, the pairs slope or the figure.
8. Ground truth at n = 131 independent of the producer's code exists for d = 6, 7, 8 only
   (30 measured targets, 30 constructed ones).
9. Predictions follow development runs; the rule's outcome was predetermined by the threshold.
10. Nothing transfers to d about 43; single run per target on a shared host; no benchmark
    record, pcc claim or validation (stated by the producer).
