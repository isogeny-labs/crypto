# Frozen study — Prime31 F3 batched quadratic roots (2026-11-19)

**Source curve:** Original `PRIME31` in `research/prime31_ic_20261115/native/lib.rs`, p=2147483647, a=847514846, b=2087444724, n=2147446831, G=(625037715,2100627251), cofactor 1, not a deliberately weak curve. Pin original crate source at `1df714645aa683cf975bc76fcacb9842cb4780fd`. Rust 1.100.0.

**Hypothesis:** Use the degree-2 Semaev F3 equation to recover the second factor-base x from the public R and first factor x, with all 31 denominators inverted in one Montgomery batch. This may reduce the field-inversion and wall costs of a *two-summand primitive*. It cannot by itself establish a non-generic 8-summand, high-yield or complete ECDLP win: the F3 roots equal x(R±P), and are generic-group implementable.

**Derivation (fixed):** For E:y²=x³+ax+b and public x(R)=r, factor x(P)=u, treat F3(u,v,r) as a quadratic in v:
`A=(r-u)^2`, `B=-2[(r+u)(ru+a)+2b]`, `C=(ru-a)^2-4b(r+u)` mod p.
Discriminant `B²-4AC =16 f(r) f(u) =(4 y_R y_P)^2`. If A != 0, roots `v=(-B±4y_R y_P)/(2A)`; otherwise solve the remaining linear `Bv+C=0` (and exclude the point-at-infinity root). They are exactly the x coordinates of R±P when finite. Reconstruct all ± factor-base signs and verify each solution by original-curve EC group addition.

A separate same-target control evaluates R±P_i using original Rust EC addition and only the public x→index dictionary. No sum-of-two-point lookup table may be built. Both algorithms emit all signed ordered witnesses and must agree exactly.

## Amendment A — production-method comparator added before three-arm execution (2026-11-19)

A broader GitHub code search, executed **after the two-arm protocol and first source-bound launch**, located a direct implementation of the exact quadratic F3 two-decomposition via batched subtraction in `examples/semaev_rootfind_scaling_bench.rs` and `examples/semaev_rootfind_nist_bench.rs` on main. The native `prime_fast::Fp64` method predates this study. Thus the candidate is **not a new algorithm**; treating an improvement versus unbatched affine group subtraction as a new contribution would be an unfair comparison.

Freeze a third production-method reference before the *amended* benchmark: reimplement the published Rust direct-subtraction expression `x(R±P_i) = ((y_R∓y_i)/(r-x_i))²-r-x_i` with one batched inversion for all 31 `r-x_i` denominators. Preserve its exact root/lookup logic, but repair the singular `r=x_i` branch for complete all-signed-fibre comparison by using the tangent root `x(2P_i)` (batch denominator `2y_i`, one linear candidate). Charge the same full-witness verification after matching a public x. This comparator is named **`direct_batch`**, not a new invention. Read `examples/semaev_rootfind_scaling_bench.rs` and `src/cryptanalysis/prime_fast.rs` as prior art.

All three arms must run on the same **frozen 351 public Q** with eight alternated paired repetitions, full 64/64 planted recoveries and exact full-fibre equality. Report field mul/inversions, group verifications and median wall times for **F3 discriminant**, **preexisting direct-batched chord method**, and **unbatched generic EC reference**; only a gain versus the direct-batched arm is an implementation improvement. Any F3 slowdown is a valid negative result. The primary outcome of this amendment is **F3 versus direct_batch**, and the original unbatched comparison becomes context-only. The 31 singular targets are mandatory so the production path's zero-denominator skip cannot silently omit solutions. No DLP solver or novelty claim.

This amendment changes only the comparators and reporting, **not** seeds, factor base, curve, cohort sizes, correctness rules, or sample construction; a previous two-arm run cannot count as a three-arm result. Record source-specific commit and check independently.
