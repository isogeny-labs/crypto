# Prospective Q0–Q4 supervisor — source only, not admitted

This private supervisor implements the existing fixed software qualification cases around exact final image ID and binary SHA arguments. No command from supervise.py has been executed. Only Python AST parsing was performed. Final bindings, independent source review, route reconciliation and prospective admission remain mandatory. This packet does not run or admit scientific work.

Invocation after review/binding is `python3.11 supervise.py --image-id sha256:FINAL --binary-sha256 FINAL --binding FINAL_BINDING.json --receipts NEW_ABSOLUTE_DIR`. binding.template.json intentionally has admitted=false and null final/build/client fields. The supervisor fails before Docker use until these joins are supplied. It checks its own reviewed source hash, exact fixture manifest and mode ledger, and the approved Docker client digest. Root supplies the independently reviewed final binary-build/source receipt hashes and exact build-info contract; the supervisor is not a replacement review of those build receipts.

The route is explicit noninteractive sudo, env-i allowlist, private empty Docker configuration and unix:///var/run/docker.sock. No build, pull, push, login, image creation or cloud API occurs. Docker create uses --pull=never against the exact already-inspected local image ID. Image environment variable names must match a separately reviewed allowlist. Inspection receipts redact environment values to hashes. No credential directory or home mount enters the container.

Q0 creates a stopped container without starting it. It reads ecbench and owner through bounded docker-cp tar output, verifies exact hashes/mode0755 and static x86 ELF properties. For ancestor permissions, the proposed explicit addition to Q0 copies /opt as a bounded64MiB tar and accepts only opt/isolab/specs/smoke-prime.json, build-info.json and the exact runtime members/directories. Any additional member stops qualification, with no fallback to broad extraction. This allows actual opt/isolab/recovery/lib traversal-mode inspection without executing an image process. Archive entries are treated as data; no extraction path is followed. UID/GID0, exact runtime bytes, metadata and explicit mode ledger are checked. The copied ELF bytes are never executed.

Q1 runs exact ecbench diagnostic-preflight with the relocated request; output must equal complete expected-report.json. Q2 changes only request digest and requires exit2 plus request hash mismatch with no success JSON. Q3 invokes exact owner --check with the wrong config digest and requires exit125 plus fresh owner: config digest mismatch. The125 exit is taken from actual fresh-owner main, rather than generalized nonzero assumptions. Q4 requires exact terminal identity/removal, unchanged fixture hashes and no writable-layer diff for active cases.

One container is owned at a time. Every case has a UUID name/owner label and exact immutable image ID. Cleanup rechecks name, label, ID and image before any kill/removal. Ambiguous create resolves only that name and label; an unresolvable identity writes CLEANUP-INCOMPLETE and retains ownership. No broad kill, prune or remove exists. SIGINT/SIGTERM enter cleanup. Docker call receipts preserve argv, monotonic timestamps, exit, stderr and bounded stdout. Client process groups are terminated on timeout/output cap; this is explicitly distinct from killing a container.

The supervisor uses a shared300-second monotonic deadline with30seconds reserved for cleanup, command caps at20seconds, and a separate20-second active-case deadline. Active calls must leave time for cleanup; kill requests use a2-second client cap. These bound orchestration requests, not guaranteed daemon responsiveness or container death. If daemon termination cannot be confirmed, qualification fails and records the owned container. File IO and daemon failures can prevent hard wall-time enforcement; no timing or lifecycle-completeness claim is made from a client timeout alone.

Active containers have UID1000, network none, read-only rootfs, cap-drop ALL, no-new-privileges, pids1,512MiB memory with equal swap limit,1CPU, only read-only fixtures plus16MiB /tmp and /work tmpfs. The supervisor verifies HostConfig, exact executable/user and mount identity before start. Default seccomp is retained; no privileged/device/host-PID setting is requested. No successful owner check or scientific payload is invoked.

Important preserved gap: the qualification draft requires effective kernel pids.max=1 before start. Docker requested HostConfig and daemon PidsLimit capability do not themselves establish that observation; a newly created container may have no kernel cgroup yet. The supervisor records requested limits and opportunistic after-start cgroup-v2 observations separately. It always leaves qualification_complete=false and effective_before_start_proved=false, with exit3 on otherwise successful cases. Closing this gap requires an independently reviewed feasible evidence/design amendment, not relabeling requested settings or after-start sampling. Until resolved, this is reviewable partial qualification machinery, not an admission-ready complete qualifier.

The source also has unresolved execution bindings: final image/client/build-info/accepted environment; local daemon route; fixture read-only mount actual identity; ancestor archive allowlist compatibility; final-image lifecycle and timing requirements outside these fixed checks. Nothing here changes controller/IAM/RBAC, publication approval, campaign budget, or deadline. Full original cohort scope is unchanged.
