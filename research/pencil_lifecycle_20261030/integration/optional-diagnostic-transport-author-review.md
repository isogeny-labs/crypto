# Optional diagnostic transport — private unapplied source proposal

This proposal passes an explicit diagnostic launch to the two existing ecbench invocation routes. It does not enable either ecbench source admission gate, execute a payload, change a mathematical method, freeze a protocol, reset a deadline, or attest a source receipt. The patch is `optional-diagnostic-transport.patch`; exact base and proposed hashes are in `diagnostic-transport-proposal/PROPOSAL-RECEIPT.json`. All five base files were rehashed before sealing. Apply the supervisor delta after the private owner-observation supervisor proposal, and the cloud delta after the private owner-exit collection proposal; this is not a patch directly against an unmodified checkout.

## Contract and byte custody

Request gains an optional `diagnostic_transport` with schema `isolab.diagnostic-transport/v1` and two entries, `computation` and `fresh`. Each contains `raw_json`, its exact decoded UTF-8 byte SHA256, and `spec_bytes_sha256`. `None` is omitted during serialization: legacy absent-option request bytes and hashes retain their prior layout. The existing legacy-layout test remains; two new synthetic contract tests cover opaque-byte round trip, independent spec bindings, malformed bounds, and the unchanged total request limit. These tests are source only and have not run.

Each launch has a 65,536-byte ceiling and a nonempty exact hash binding. The entire serialized Request still has its existing 65,536-byte ceiling, so two large launches will be rejected rather than silently increasing request admission. Request JSON escaping is transport encoding; the extracted `raw_json` string is written byte-for-byte, never parsed and reserialized as launch JSON. The actual ecbench loader remains responsible for the bounded launch schema, exact spec identity, binary, arms, and external source-receipt scope.

`spec_bytes_sha256` is explicitly the exact emitted spec-file digest, not ecbench's identity-view digest. Computation uses the existing pretty-serialized derived spec, with L0 and the exact historical computation-only label; fresh uses compact original-spec JSON plus the existing shell newline. Both expected values must be supplied independently and frozen for their respective launch. The controller only compares them. Neither raw launch nor its internal `expected_spec_sha256` is rewritten or automatically rebound. Consequently an L2 launch cannot be silently adapted to L0. Changes in serialization produce a binding error.

## Computation route

The existing trusted supervisor prepares `/work/diagnostic-input/computation-launch.json` before dropping payload privilege. It requires a real, root-owned, non-payload-writable `/work`; creates an exclusive directory/file; writes and syncs exact bytes; changes the file to 0444 and directory to 0555; and syncs directory/parent. This directory is outside `/work/compute`, which the existing code assigns to UID 1000. No existing directory permissions are broadened. Existing paths produce an error, never replacement. A partial preparation failure remains a failed attempt; no retry cleanup is invented.

The supervisor passes explicit fixed-path launch/hash/spec-hash arguments. Pinned progress validates flags, protected parent/directory, a regular root-owned nonwritable file opened with O_NOFOLLOW, a bounded read, exact launch digest, and exact derived-spec bytes. It records optional diagnostic transport hashes in the existing computation intent and directly execs ecbench with `--diagnostic-launch`. Its original four-argument path preserves original behavior and intent fields. A third unexecuted synthetic fixture covers absent/malformed arguments and wrong derived-spec binding without filesystem access.

Restoration remains the existing CRIU/PVC route and does not recreate a launch or rerun a completed invocation. Actual preservation of the added root-owned file through the qualified checkpoint/restore path has not been exercised. The launch's own output root and identities remain independently validated by ecbench; this transport supplies no authority to choose otherwise forbidden destinations.

## Fresh route

The controller's existing Job manifest receives a bounded annotation containing the exact fresh launch string. A downwardAPI volume projects that single annotation at mode 0444; a fixed read-only subPath mount exposes `/opt/isolab/diagnostic-input/fresh-launch.json`. No new ConfigMap, RBAC/IAM permission, privileged container, or object-creation flow is introduced. Kubernetes documents annotation field exposure and that downwardAPI subPath mounts do not receive updates: [Downward API](https://kubernetes.io/docs/concepts/workloads/pods/downward-api/), [Expose Pod information through files](https://kubernetes.io/docs/tasks/inject-data-application/downward-api-volume-expose-pod-information/). This is a source design; no live kubelet behavior was tested.

The wrapper checks exact optional flags, fixed path, root ownership/mode 0444, size, launch hash, and original spec-file hash before execution. It saves an exact-byte custody copy in the existing output tree, then passes the read-only mounted path to ecbench. The existing empty optional argument array expands to no arguments. Existing L2/warmup/control, full replay, and admission checks remain in place. Existing EXIT handling retains errors and uploads output; transport errors use exit 45. Annotation contents are configuration visible to principals already authorized to read the Pod; credentials must not be placed in a launch.

## Validation and remaining integration work

Only rustfmt parsing/formatting of four private Rust copies and `bash -n` on the private shell passed. No Cargo build, fixture execution, shell payload execution, cloud command, solver, cohort, or benchmark was run. This review makes no compile, runtime, performance, or scientific-completion claim. The three new fixtures are not substitutes for later permitted software tests.

Before this private patch can become a published runtime, its actual build needs to check the changed Request against all source literals, the exact pinned dependency graph, and existing request/hash fixtures. Synthetic manifest and root-owned fixture tests should cover the produced arguments, mounted bytes, permissions, rejection, and legacy absence. The fixed mount's parent behavior and runtime availability of existing/core utilities remain runtime verification items, not established facts. A rejected optional transport must remain a recorded failed attempt, never fall back to an uninstrumented run. The reader intentionally relies on the existing trusted supervisor/kubelet boundary; it does not defend against an authorized root owner rewriting its own files.

The independently frozen L0 and L2 launch documents, correct current binaries, complete outer resource/custody accounting, and existing prospective admission remain separate inputs. This patch supplies transport only and does not relax those inputs or create new scientific conditions. Ecbench's two disabled admission gates are untouched because no ecbench source is part of this patch.
