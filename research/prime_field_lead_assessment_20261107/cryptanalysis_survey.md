# Survey of /home/user/cryptanalysis: ECDLP and index calculus on prime-field curves E(F_p)

Read-only survey, 2026-11-07. Paths are relative to /home/user/cryptanalysis. Nothing was built or run; all numbers are quoted from committed docs/READMEs/JSON. Per the repo's own rule ("Sabotage is assumed"), nothing below carries a pcc claim id I could verify; where the source labels itself `[pcc:unverified]` I repeat that, and every other figure is a producer assertion from a committed file, i.e. `[pcc:unverified]` from my side. I did not read every one of the 455 experiment dirs: ~139 `prime-j0-*`, ~79 `hecke-*`, ~52 `n83-*`, ~34 `koblitz-*`, ~29 `ecc2k130-*`, ~16 `groebner-*` were sampled/clustered (marked "inference" where I generalise).

## 0. Bottom line

* The repo's own headline: "This repository contains no ECDLP speedup, and none is claimed" (README.md status note). For prime-field curves no sub-sqrt(n) method exists here; every prime-field index-calculus (IC) measurement that is cited sits above matched rho.
* The only prime-field IC rows with numbers (in papers/ecdlp-constant/sec-indexcalc.tex, imported from sibling `crypto`): full-pipeline S = 56.8 on a 23.4-bit prime-order curve, 14.5x matched rho (S=3.93), 64.1x the counting floor; fitted exponent 0.60 (above 0.5). The docs/ic baseline ledger (docs/ic/baselines.json) has five rows and ALL are binary Koblitz (n = 19, 41, 53, 61, 83); there is no prime-field E(F_p) IC baseline row in this repo.
* Where measured improvements exist for prime fields they are constant-factor rho engineering: negation-map rho (group_ops ratio 0.748 pooled, 20-40 bits), GLV table/cycle-escape (0.957-0.967 and 0.658/0.768), Z_p^* IC instruction halving (2.30x-2.36x Ir). Wall-time follow-ups are mixed (see §3, §7).
* Certicom: only ECCp-131 and ECC2-131 (aliases ECCp-130/ECC2-130) parameters are encoded (suite/src/ecc/certicom.rs, crates/hashed-ecdl-tensor/examples/eccp131.json). ECCp-79/89/97/109 are NOT defined as targets: `suite/examples/eccp79_rho.rs` is a generic 79-bit-scale rho example whose challenge constants are deliberately left `None`. No Certicom prime-curve scalar has been recovered.

## 3. experiments relevant to prime-field ECDLP (455 dirs total; prime-relevant listed)

**p256-isogeny-search-20261005** (1,017-line README). Hypothesis: a cheaper curve in the P-256 F_p-isogeny class makes rho faster. Facts: |D_pi| = 3*5*456597257999*1428624589419343516204097*46523541035814968339936406074986559003387, fundamental, so Z[pi]=O_K, End = O_K for every curve in the class, no vertical volcano levels, no j=0/1728, no low-norm endomorphism (lower bound ceil(|D|/4)). Measurement: registry grew to P-256 plus 15,889 explicit neighbours through depth 45 (degrees 3/5/11/13; one-hop through degree 199); matched native Montgomery/projective/64-batch rho, 15 one-second trials each. Result: every paired 95% interval contains 1.0; best earlier native 1.0031x [0.9847, 1.0217]; depth-45 extension 1,392 curves, 32 screening hits (1.022x-1.128x) all failed the fresh 30-trial holdout (largest 1.0387x [0.9912, 1.0884]); six early exploratory positives remain open for isolated replay; mapping cost 0.65-0.97 ms per public key; normalized-3b coefficient audit: smallest retained coefficient 243 bits, zero curves pass the 32-operation gate. Conclusion: null (bounded traversal, not exhaustive class-group enumeration). No pcc id given in the README.

## 9. Gaps and cautions for the caller

1. No pcc claim ids appear in the READMEs I read (only `[pcc:unverified]` tags in docs/ic/structured-prime-ic-20261104 and benchmark rows); run `python3 tools/pcc/pcc.py` if standing is required. I did not run it.

3. The prime-field IC code in this repo (prime_orbit_index_calculus.rs, ec_index_calculus*.rs, ic_boundary.rs) is toy-scale (<= 62-bit fields); its own header says relation collection costs about c r/w (linear in r, above rho's sqrt r) while one descent costs about r/(wm); at 256 bits precomputation is about 2^256/w. The repo's design intent is to measure the constant, not break sizes.
4. Inference: because the baseline ledger and the success criterion are expressed in the binary Koblitz family (n <= 83), any "improvement over the index-calculus baseline" for E(F_p) would first need a prime-field baseline row; none exists now.
5. The sibling repos `crypto`, `crypto-autoresearcher` hold the ic_planner_exhaustive_20261026, ic_boundary ledger, and research-kb that this repo cites; I did not access them.
