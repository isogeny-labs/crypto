# ic-acct-6: completing the archive's `bitop/v1` accounting

Frozen before any re-run of this study. Written 2026-10-26 (study opened
2026-10-21).

## Question

Of the archive's verified, non-warm-up ecbench records (every
`research/**/records.jsonl`), 19,931 index-calculus records price
`complete: false` in `bitop/v1` and 56 cannot be priced at all. How many can be
made complete, and how?

Two routes, kept apart:

- **Phase A (rules, no runs).** A counter that committed records already carry
  but no rule priced gets a rule where a defensible primitive mapping exists
  (`docs/units/BITOPS.md`, "Extensions", 2026-10-21). No primitive weight
  changes (`committed_vectors_are_frozen` passes unchanged). Work that was never
  counted is not invented: the five index-calculus items
  (`gauss_column_scans_and_pivot_inversions`, `relation_row_construction`,
  `walk_bookkeeping`, `table_insert_attempts`, `base_index_builds`) and the
  solver gaps stay on the records that lack the counters. The effect is
  `BEFORE_AFTER.md`, generated by `examples/ic_acct6_archive.rs`.
- **Phase B (re-runs).** The never-counted work can only be counted by running
  the same computation again on the instrumented binary. This file is the plan
  for that.

## The re-run rule

A re-run of a committed session is:

1. **the same spec**: `specs/<name>.json` is a byte copy of the committed
   session's `spec.json` (its sha256 is listed in `tranche.json` beside the
   original's path), so the spec id, workloads, targets, arms and the
   measurement seed are the committed ones;
2. **a new session**, run by this branch's build (`target/release/ecbench`, its
   sha256 in the task card) into `sessions/<name>/`; it gets its own session id
   and binary sha;
3. **audited**: `ecbench verify --dir sessions/<name> --replay 2 --exit-code`
   must exit 0 (every integrity check, and two measured runs re-executed with
   identical counts), written to `sessions/<name>/verify.json`;
4. **priced complete**: every verified non-warm-up record of the new session
   must price `complete: true` under this branch's rules. A record that does
   not is reported with what it misses; it is not dropped.

The committed session is never touched. The re-run does not replace it in any
table by itself; a table that wants the complete price cites the new session.

Counts only. Runs are L0 (`--cpus 1 --allow-busy`, a shared 4-vCPU host with
other agents building), so their wall times are descriptive and no timing
claim is made. Each session holds the host's shared build lock while it runs
and while it is audited (`run_tranche.sh`), so other agents' builds interleave
between sessions.

## Which sessions can be re-run unchanged

`ic_acct6_archive plan` (on `breakdown-after.json`) checks, for every session
with an incomplete or unpriceable record, that this build:

- parses and plans the frozen `spec.json`;
- arrives at the committed spec id;
- resolves every arm to the committed method id;
- plans as many executions as the session recorded;
- has every native backend the spec names.

Sessions that fail any of these are not re-runnable unchanged and are listed
with the reason: the CM-folded sessions need `/workspace/native-deps/cm-folded*`
backends pinned by sha256 that this host does not have; a few sessions have no
frozen spec or were interrupted.

## Priority

1. Sessions whose study feeds the index-calculus leaderboard: a
   `research/<study>` path named in `scripts/build_ic_leaderboard.py` or
   `docs/ic/LEADERBOARD.md`.
2. Then by number of incomplete records, largest first.

Sessions that cannot be re-run unchanged sort after the re-runnable ones of
their group. The full ordered list is `PLAN.md` (generated from `plan.json`).

## Runtime estimate

A session's estimate is the summed `time.process_wall_ns` of all its committed
records (warm-ups and failures included), on the host that ran it. Audit
replays add two runs per session.

## First tranche

Budget: 3 hours of wall time on this host from the restart of 2026-10-26
04:37 UTC, builds included. The tranche takes re-runnable sessions in priority
order, skipping any whose estimate exceeds the budget left when it is reached,
and launches no session after the budget is spent. It runs through one
frozen-command task card (`cards/`), executed with `tools/task_card.py run`,
whose receipt is committed.

## What lands

- `BEFORE_AFTER.md`, `breakdown-before.json`, `breakdown-after.json`: phase A.
- `plan.json`, `PLAN.md`: the re-run plan, with the tranche marked.
- `specs/`, `sessions/<name>/` (records, session, verify.json), `logs/`,
  `cards/`: the tranche.
- `TRANCHE.md`: per re-run, verify exit status, records, and complete counts;
  `breakdown-tranche.json` prices the new sessions.
