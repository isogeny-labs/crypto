## 2. Correctness of the new `PairTable`

**Code read** (`git show 5eaf9fa237:src/cryptanalysis/prime_fast.rs`, lines 1112-1243): `bits_p` = bit length of p-1; `target_bits = max(4, floor(log2(max(len, 32) / 2)))`; `shift = bits_p - target_bits` (0 if negative); `nb = ((p-1) >> shift) + 1`; `starts` has `nb + 1` u32 counters (count at `(x >> shift) + 1`, prefix sum), a stable scatter by `cursor`; `max_x` from the unsorted entries. Every canonical x < p satisfies `(x >> shift) <= nb - 1`, so the scatter cannot go out of range. `lookup(x)` returns the empty slice when `(x >> shift) + 1 >= starts.len()` and otherwise the bucket filtered by exact `e.0 == x`. The legacy branch (`sorted`) keeps one bucket (`starts = [0, len]`, `shift = 63`), narrows by `partition_point` and then applies the same (redundant) filter. Consumers guard with `xc <= pairs.max_x()` and use `for &(_, j, k_raw) in pairs.lookup(xc)`.

**Differential test** (`<scratch>/mini/examples/diff_pairtable.rs` on a white-box copy of the committed file with read-only accessors appended; output `out/diff_pairtable.txt`, `out/diff_pairtable_big.txt`). For each instance both layouts are built in the same process (`IC_PAIR_SORTED` toggled), an oracle is computed with the full affine group law (`curve.add`, not the batched-inverse path), and the following are compared: entry multisets (new = legacy = oracle), `max_x`, the bucket invariants (`starts` endpoints and monotone, every entry in bucket `x >> shift`, each bucket equals the stable construction-order bucket, `shift` and `nb` equal the independent formula), and `lookup` for the query sets below.

- Tiny and small curves (8 to 24 bits, both residues, fb in {8, 9, 16, 33, 64}, lanes in {1, 7, 256}, extra in {0, 6}, seeds 1 to 6; 6 120 cases, 255 631 relations): sequences equal in 5 624, **multisets equal in 5 864 (95.8%)**. Mechanism (code read, not instrumented): within one target the candidates come out in a different order, and in `collect_setup_batched` the `break` on `rels.len() >= needed` leaves only the candidate loop, so after the cut each remaining lane of the round still contributes its first candidate; where a lane has several candidates, which one comes first depends on the layout. In `ic_multi_solve_ex`'s per-target phase the decision (done / restart / continue) is a function of the candidate multiset, and the RNG is consumed identically, hence the identical results. So the statement holds as: "which valid relation is found may differ; validity and the final logs do not".

**Latent edges** (none reachable from the committed callers; none changes a verdict):
- E1. `lookup(u64::MAX)` on the bucketed layout panics when `shift == 0` (2 014 of 2 014 such instances; release build: `b + 1` wraps to 0, then `starts[usize::MAX]` is out of bounds; debug build: add overflow). For `shift > 0` it returns empty (3 884 of 3 884). Callers pass canonical x < p and guard with `xc <= max_x`. The legacy layout returns empty.
- E2. `starts` are u32: more than 2^32 entries (fb >= 65 536) would wrap silently in a release build; the pair table would already need 64 GiB.
- E3. Peak memory: `let entries = sorted;` shadows but does not drop the unsorted vector, so build holds 2 x 16 B x fb^2 until it returns (section 5).
- E4. In the three collectors `seen.insert(merged)` runs before `relation_holds`; a rejected candidate still claims its key. It cannot matter while the lookup is exact, but the mutant without the exact-x filter shows the effect (`determined` 260 to 266, section 4).

## 4. Correctness, certificates, mutation tests

**Certificate discipline.** The committed rows carry only `ok` (an in-process comparison with the planted k). No certificate file exists and the planted logs are not stored. The run is deterministic, so I re-derived certificates by replay. `diff_relations.rs` calls `ic_multi_solve_ex(&c, g, &qs, fb, 6, 5_000_000, ins + 1, true, true)` exactly as the example does (same seeds and target formula) for both layouts on the 28 evaluation instance/T cases, checks `k*G == Q_t` by `curve.mul` for every returned log (0 wrong; `ok_new = ok_old = T` in every case), and dumps p, a, b, G, the determined factor-base logs and 300 random targets per case (planted k, Q_t, returned log, for both layouts). `verify_logs.py` (Python ints only, no shared code) checks G on the curve, `x_j*G == F_j` for each dumped factor-base log, `k*G == Q_t` for the planted k, and returned == planted. Result (`out/verify_logs_python.txt`): **28 files, 1 680 factor-base logs and 16 800 target-log records (8 400 sampled targets x 2 layouts) verified, 0 failures**. A failed certificate would have made the run `invalid_measurement`; none failed. The artifact itself carries no certificate; this is the validator's replay, not a producer artifact (correction R7).

**Mutation tests** (`mutants.rs`; mutants generated by `gen/mkmods.py` from the committed file with each patch asserted to match exactly once; bucketed layout; 25 bits residue 3, T = 300, fb = 323, `max_walk` 20 000; `out/mutants_clean.txt`):

Conclusions. (i) The only assignment to `res[t]` in the batched branch is behind `curve.mul(Some(g), k) == Some(qs[t])` (lines 2034 to 2035 of the frozen file; removing it in the controls produces 300 wrong logs that the checker flags, so the test has teeth). (iii) A corrupted lookup or sort (M1, M2, M6) cannot yield a wrong log, it only costs time or leaves targets unsolved (M2, M6 return 77 and 80 of 300 within the 20 000-round cap). (iv) M7 (all factor-base logs shifted by one) still returns only correct logs because a relation with `sum of signs = 0` is eventually found; the final check would reject the others. The "determined" flag is not a correctness signal when relations are wrong; the final guard is.
