## 4. Source review of the word-sized sweep (`ec_index_calculus.rs`, `WordSweep`, `find_one_relation_sweep_with_index`)

Read at `2fb74a63dc`.
- **Same candidate set and order.** `candidates(x1, x2)` computes the coefficients of `semaev_s3_in_x3` term for term: A = (x1-x2)^2; B = -2[(x1+x2)(x1x2+a)+2b]; C = (x1x2-a)^2 - 4b(x1+x2). Linear case `qa == 0`: `qb == 0` gives no candidate, otherwise one candidate -qc/qb (the `BigUint` loop: `continue` on `qb == 0`, `qc.neg().mul(inv)`). Otherwise disc = qb^2 - 4 qa qc; `disc == 0` gives sqrt 0 and **both** signs are tried in both implementations (the second is a repeat); a non-residue gives none; roots are (-qb + s) / 2qa for s = +sqrt, then s = -sqrt, in that order. The square root is `sqrt_mod_p_u64` in both: `sqrt_mod_p` delegates to it for word primes (line 668 to 674), so the returned root, and hence the sign order, is identical by construction (also for p = 1 mod 4, Tonelli-Shanks, which is every v7 prime; the repository unit test uses only p = 271 = 3 mod 4).
- **Loop and RNG.** Factor-base entries are visited in order, `Point::Infinity` skipped in both; the first successful `try_finalise` returns in both; after a failed trial both `continue`; both draw `a` and `b` before the branch and nothing in the branch draws randomness, so the RNG streams stay aligned (confirmed empirically below).
- **Bitmap.** `in_fb` is indexed by `x` up to the largest factor-base x; a candidate above it fails `(c as usize) < w.in_fb.len()` and is skipped, which is exactly what `x_to_idx.get` returning `None` does in `try_finalise`. `in_fb` and `x_to_idx` are built from the same factor base, so the key sets are equal. Candidates are reduced below p, so no out-of-range index.
- **Arithmetic bounds.** `WordSweep::new` returns `None` unless p is a single odd word with 2 < p < 2^40; sums of two residues stay below 2^41, products go through u128 (`(u as u128 * v as u128) % pw as u128`, below 2^80), so no overflow; with `None` the code falls back to the hoisted `BigUint` sweep silently. Latent (not reachable from the CLI, which rejects a, b >= p): `WordSweep::new` does not reduce `curve.a`/`curve.b` modulo p, and `in_fb` allocates up to `max_x + 1` bytes, which for a non-standard factor base near p would be large (the staged solver uses `build_factor_base`, smallest x, so max_x is about 2 fb).
- **Gating.** `IC_FAST_SWEEP=1` (only in `ec_index_calculus_dlp_staged_with_rng`) turns on both the hoisted index and `WordSweep::new`; `IC_SUM_TABLE=1` takes precedence over any sweep. With no `IC_*` variable `word_sweep` and `hoisted_index` are `None` and the call is `find_one_relation_counted_with_rng`, which passes `None`. `git diff 22c1fe13a1^ 22c1fe13a1` shows the commit that added the word sweep changes the default path only by adding that `None` argument and the `if let Some(w)` branch; the `BigUint` loop is untouched. Not rerun against a pre-PR binary: the merged-panel `rows.jsonl` was moved to the artifact store and is not on disk.
- **Independent equality, relation level** (build B; `scratchpad/hook.rs`, `zz_val_eq.rs`, `run_eq.py`): the repository's `find_one_relation_sweep_with_index` called with `word = None` and `word = Some(..)` on two `StdRng`s with the same seed, 30 relations per cell, comparing trial count, `coef_a`, `coef_b` and `entries`, and checking the two RNG streams are still in step: **90 instances x fb {3, 4, 6, 8, 16, 32, 96, 256} x seeds {1, 2, 3} = 2,160 cells, 64,800 relation pairs, 34.4 million trials, 0 mismatches, 0 RNG desyncs.** This covers p = 1 mod 4 and both anomalous curves, which the unit test does not.
- **Independent equality, black box** (evidence binary; `scratchpad/diffEhEf.py`): Eh and Ef at the same fb and seed on all 90 instances, fb {4, 8, 16, 32, 96, 256, 512}, seeds {1, 2}: **1,260 pairs, 0 differ** in scalar, `trials_total`, `relations_collected`, per-relation trial min/median/max, attempts exhausted and factor-base size (2.38 million trials, 168,840 relations, 0 exhausted attempts, all recovered).

## 5. Fairness of the arms

**5a. Which arm uses what.** All five arms run `build_factor_base` on `BigUint` field elements, the same `relation_point` (`IC_SHAMIR` unset after scrubbing, so mode 3, `g.double_scalar_mul_vartime`, the fast point path), `sqrt_mod_p` through `sqrt_mod_p_u64`, the u64 elimination path (`gaussian_eliminate_mod_u64`, n < 2^64) and the constant-time `scalar_mul` for verification. A: x-index rebuilt per relation, `BigUint` sweep, fb 8, extra 64. Eh: hoisted index, `BigUint` sweep. Ef: hoisted index and the u64 sweep body (u128 `%` modular multiplication, Tonelli-Shanks square root and extended-Euclid inverse per candidate). D: no sweep; pair-sum table with `BigUint` (x, y) hash keys, two `add_vartime` per pair, one lookup per trial. Dw: the same table plus a 32-arm r-adding walk restarted every 32 steps (`add_vartime`, (a, b) tracked mod n). So the point path is common to A, Eh, Ef and D; the walk is the only arm that changes it. Everything the table and walk still do through `BigUint` (keys, factor base, step bookkeeping) is untouched, so D and Dw are not fully optimised either.

**5b. Is each arm at its own optimum?** I re-probed the tuned arms on the **tune instances only** (30 instances x seeds 1 to 4 = 120 cells per fb, finer grids, shuffled; 4,080 runs, all recovered; `scratchpad/fbprobe.py`, `fbprobe_rows.json`): Eh {128: 29.1, 160: 27.3, 192: 24.7, 224: 23.5, **256: 21.7**, 320: 22.5, 384: 24.8} frozen = best; Ef {48: 11.2, 64: 10.8, 80: 10.4, **96: 10.4**, 112: 10.3, 128: 9.92, 160: 10.1, 192: 9.91, 224: 10.9, 256: **9.83**, 320: 11.8} frozen/best 1.055; D {16: 2.18, 20: 1.71, 24: 1.56, 28: 1.47, 32: 1.60, **40: 1.40**, 48: 1.82, 56: 1.96} frozen/best 1.14 (means 1.02); Dw {8: 0.74, 10: 0.64, 12: 0.58, **14: 0.531**, 16: 0.544, 20: 0.539, 24: 0.60, 28: 0.65} frozen/best 1.025. Re-tuning every arm to its probe optimum moves D/Ef from 0.154 to 0.142 and Dw/Ef from 0.052 to 0.054 on the probe data: the frozen settings are near-optimal and the tuning is not a source of asymmetry.

**5d. Is Ef the strongest implemented sweep? No.** `src/cryptanalysis/prime_fast.rs` ("native-width prime-field ECDLP engine", results in `RESEARCH_PRIME_FAST_ECDLP.md` and `research/prime_fast_bench_20261008/`; also `examples/prime_ecdlp_fast_bench.rs`, `examples/fb_hyperparam_sweep.rs` and the `ic_framework` plugin oracle) implements `ic_solve(summands = 2)`: Montgomery arithmetic on u64, `collect_relations` as "a 2-decomposition sweep ... one batched subtraction per factor-base element plus an array lookup, no square root, no inversion per element" (S3 root = x(R -+ F_i), one Montgomery batch inversion per target), relation sets documented identical to the S3 sweep's, `R <- R + G` between unproductive targets, u64 Gauss-Jordan, and a group check of the recovered logarithm before returning. The campaign documents never mention it (`grep` of the campaign directory for `prime_fast|ic_solve|collect_relations`: no hit). I measured it (`scratchpad/build_src/examples/zz_val_fastic.rs`, `pf_probe.py`; in-process `total_ms` of `ic_solve`, which covers factor-base build, relations, linear algebra and verification; cold process per run; all runs verified against the planted log):

Paired ratios (median [by-instance bootstrap]) against the stored rows: **PF/Ef 0.079 [0.074, 0.087]** (Ef is 12.6x higher; 120/120), **PF/D 0.530 [0.506, 0.567]** (D is 1.89x higher; 120/120), **PF/Dw 1.464 [1.355, 1.585]** (the walk is 1.46x lower, 0.683 [0.631, 0.738] as Dw/PF; PF wins 13/120). - Limits of this probe: validator-side, exploratory, single host, a different harness (in-process timer, no CLI process), not a frozen protocol, and run on the producer's evaluation instances (but tuned only on the tune instances). No other stronger implementation: `crates/` holds toy tensor/hashed ECDL code ("no speedup is claimed"); `prime_orbit_index_calculus.rs`, `ec_index_calculus_j0.rs` need automorphisms (j = 0 or 1728) and do not apply to these generic W curves; `semaev_decomp.rs` is binary-field S4.
