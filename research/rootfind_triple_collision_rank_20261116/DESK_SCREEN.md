## Mathematical check

Let `F_i` be physical factor-base points and let `v(i)` be their signed folded column vector modulo subgroup order `r`. The existing folding contract says `[h]F_i` equals the linear combination encoded by `v(i)` in the prime subgroup, with `h=4` on these three curves. If two verified triple sums agree, `F_i+F_j+F_k=F_u+F_v+F_w`, then applying `[h]` gives `(v(i)+v(j)+v(k))-(v(u)+v(v)+v(w))=0` as a homogeneous row. If the sums are negatives, add the two triple vectors. If one triple sums to the identity, its own vector is a row. These are algebraic statements conditioned on the existing folding contract; the proposed executable checks each full point identity before accepting a row. [pcc:unverified]

The true nonzero factor-base log vector lies in the nullspace of every such homogeneous row, so these rows alone have rank at most `C-1` over the prime order `r`. At that ceiling, one verified known-generator relation fixes the scale of the base logs and one verified challenge relation permits scalar recovery. Any fixed construction that omits either relation cannot complete a DLP. Pair-collision seed rows and the torsion row enter first, so new independent rank is measured **incrementally**, not counted by duplicate keys. [pcc:unverified]

## Cost and relevance screen

The fixed bases have `B=33,139,275` physical points. The exact counts of unordered triples with repetition, `C(B+2,3)`, are `6,545`, `457,310`, and `3,504,050`. The source test will exhaust the K13 domain and cap K19/K23 at 32,768 unique generated triples. These are mathematical candidate counts, **not** observed collisions, usable rank, time, or speedup. Random raw-triple birthday estimates are unsafe here: zero, inverse pairs, repeated points and orbit folding create formal dependencies. The screen records duplicate draws, full sums, identity sums, verified collisions, zero/dependent/independent rows and elimination work before any cost comparison. [pcc:unverified]

The direct Frobenius pair-table path is a separate, weaker fit for this exact K13 standard-subspace workload: `FrobeniusPairTable::build` requires a base closed under Frobenius, whereas the pinned physical base has 33 points and is generated as a dimension-five standard subspace. Its current source returns `None` when an orbit member is absent. This screen instead uses the same physical base and folding columns as the existing collector. This is a source-level applicability check, not an execution result. [pcc:unverified]
