# Deviations, implementation choices and development history for G2-decoupled-AB-projection-arm

Protocol: PREREGISTRATION.md (hash in PREREG.sha256, re-verified by run.sh). Items below are deviations or choices the preregistration left open. Items marked EXPLORATORY label the affected results.

1. **Run order (task instruction: positive control first).** PREREGISTRATION section 8 lists curves, lemma, semaev, tables, analyze. run.sh runs curves, then `g2_pcsynth.gp` (added positive control: the interval code of `g2_ana_lib.gp` must report rho < 1 for a synthetic arm that is truly 2x cheaper, and must have a null interval containing 1), then `g2_semaev.gp` (PC5, Semaev solvers vs group-law tables: the registered positive control for the instrument), then `g2_lemma.gp` (NC1, audit, NC4), then the tables, then analysis. The content of every registered step is unchanged. The registered PC1 (injection x2 and x0.5 on real data) is computed in `g2_analyze.gp` because it needs the recorded counts.
2. **Added synthetic positive control** (`g2_pcsynth.gp`, `out/pcsynth.csv`): not in the preregistration. It uses a fixed seed (777), two synthetic curves with synthetic counts, and the same `rhos`/`cboot`/`tboot` code as the real analysis. It is an addition, not a replacement for any registered control.
3. **Development runs before the hash freeze.** The scripts were developed with test runs into `dev/` (tiny N=16 smoke tests, then one complete run of every stage into `dev/out`, including a complete analysis). The author saw those outputs (all numbers of the analysis report). Changes after seeing them were limited to: a parenthesis/syntax fix in the H2 block, a CSV bug fix (the arm names contained commas, which shifted columns of `results.csv`; names now use ';'), labelling arms 4 to 6 as NA when the coupled arm was not run (N > 40), the plot script handling NA, and extra reporting lines (H4 count of second-rho values below 1, per-solve wall ratios, the JSON summary). No hypothesis, threshold, grid value, seed or definition was changed after seeing the dev numbers. Because all seeds are fixed, the frozen run is expected to reproduce `dev/out` exactly for every non-timing quantity; wall-time numbers differ because they are timings.
4. **Unspecified details resolved by the implementer.**
   - Curve selection: the c-th valid curve of the stream seeded `1000*p+c` (as E3). Extension curves c=3,4: same rule. Extreme-twist curve: among the first 400 admissible draws of `setrand(31000+p)`, "admissible" = nonsingular, #E prime and not p, #E' odd, gcd(#E,#E')=1 and E' cyclic (the cyclic condition is the E3 selection rule; the discrete-log machinery needs it), smallest #E' (first on ties). The p=211 extreme curve has a=0 (j=0), so it has extra automorphisms; this is within the registered rule and is reported as is. The curve label for the extreme curves is c=9 (target seed `7000+10*p+9`).
   - Target classes: class F uses the E3 draw `draw_targets(7000+10*p+c)` (A,B as E3); class S uses the same A with B forced to O (R = A*GE). NC2 redraw of B uses an independent stream `setrand(8000+10*p+c)`.
   - "Independent E-relation" = distinct x-sets of j E-type x in V whose signed sum (some sign vector) equals A (counted once per x-set, as E3's D counts). For the coupled arm X the independent E-relation count is the number of distinct (target, E-part x-set) pairs among its hits (`Xe`); E3's own "rho_gen" (all X hits with j <= m) and the all-j count are reported as secondary arms 5 and 6.
   - D* = argmin over j in [m,2m] of Z_D(j), recomputed inside every bootstrap resample. D_m was the argmin in every cell (the analysis prints D*).
   - "Best twist arm" (arm 3, `PF best`) = the minimum over the sweep j=1..2m-1, k=2m-j and the two registered cells (m,1), (m,m), with the full twist work charged. Sweep entries with j < m have fewer E-terms than D_m and are not like-for-like; the printed j*10+k code shows which arm won (it was (m,1) in every cell).
   - Pooled cell = (family, p, N), ratio of totals over the 2 primary curves of that p; the curve-level bootstrap (B=10000, seed 9002 per cell) therefore resamples only 2 curves and has at most 3 distinct outcomes. The registered caveat applies: these intervals are coarse and conditional on the curve family. Target-level intervals (T=200, B=2000, seed 9001) are given for single curves (primary and extreme). The extension pool (c=1..4) is exploratory. The "pooled grid" rows sum totals over the E3 N grid (A: N=16,24,32,40; B: N=12,16,20) and resample the 6 (A) or 4 (B) primary curves.
   - Zero yield: bootstrap resamples with zero yield give an infinite cost; the point estimate of an arm with zero total yield uses the rule of three (yield 3 per curve, flagged `lower_bound=1`). The coupled arm is not run for N > 40; its rows are NA.
   - Rank check: per target, rank over Q of the 0/1 incidence matrix (columns x in V) of the A-sets of size m, of the B-sets of size m, and of the pair rows (union of an A-set and a B-set, all pairs, capped at 1500 rows); the check is rank(A) <= Y_D, rank(B) <= Y_T and rank(pair) <= rank(A)+rank(B). The cell-level stacked rank of all A-sets over targets and the number of distinct A-sets are also recorded in `out/tables_*.csv`.
   - NC1 for even-order curves: for a class-S target the registered projection gives B' = (R - pi R)/2 = O identically, so B' != O cannot occur for class S. The projection's "/2" on a group of even order is taken as multiplication by the inverse of 2 modulo the odd part of #E(F_{p^2}); it then returns the odd-order component of R, so A' != R for targets of even order. Both counts are reported. The E3-style decomposition audit (4-subsets of V0 = 0..19, with sign vectors up to global sign, counted twice) is run on every curve, odd and even, and is where B != O appears for the even-order curves.
   - NC4: all E-only 4-sets of E-type x in V (N=24) with all sign vectors, summed in the actual F_{p^2} group law and compared with the 200 class-F targets (expected 0 hits) and with the 200 class-S targets (detector control, many hits).
   - NC3 (timer null): D2 timed against an identical second call of the same function (arm `D2c`), 7 interleaved repeats; the interval is the two-sided 99% Student-t interval of the mean of the 7 per-repeat ratios (6 d.o.f., t=3.707).
   - Wall cells and arms: (101,12), (101,16), (211,16), (211,24), (401,16), curve c=1, 10 targets, 7 interleaved repeats. Arms: D2 (class S, given x_A), D2c, T2 (twist, given X_B), PROJ (F_{p^2} projection only), PS (projection of a class-S target plus D2), PF (projection of a class-F target plus D2 plus T2), D4 (numeric S5 by resultant, E-type 3-subsets), X4 (cells with N <= 16). Inner repeats (500 for D2, D2c, T2; 200 for PROJ, PS, PF; 1 for D4, X4) divide out getabstime's 1 ms granularity; reported times are ms per target. Medians and minima over the 7 repeats; `/proc/loadavg` and `nproc` are logged per repeat in `out/semaev_runs.csv`. No arm exceeded the 600 s cap.
   - H6 "per relation" is reported per target and per root-solve; the registered orderings (P > D_m >= 1, P < X) are evaluated on the per-target medians.
   - PC4 and NC2 use the same definitions as E3 (yield within [0.8,1.25] of the model C(N_E,m) 2^m / l; two-sample permutation test of the (j=k=m) pair count with 2000 shuffles, add-one p-value, seed 9002).
   - E3 cross-check: `g2_analyze.gp` reads E3 `out/results.csv` and compares D_m totals, X(j<=m) totals and E3's rho_gen cell by cell for the 36 E3 cells.
5. **Resource handling.** At most 2 gp processes at once. No Rust, no builds, nothing under `target/`.
6. **First frozen run aborted in the Semaev stage; script fixed and re-frozen (v2); the whole driver was re-run.** The first complete `run.sh` run (hashes in `SCRIPTS.v1.sha256`; all outputs kept in `out_run1_aborted_semaev/`) stopped inside `g2_semaev.gp` after the third wall cell (211,16): the D4 arm (inner repeats 1) measured 0 ms on one repeat (getabstime has 1 ms granularity), so a per-repeat ratio with D4 as denominator divided by zero ("impossible inverse"), and gp aborted the script (rc 0 because gp batch mode returns 0). Consequence in run 1: wall cells (211,24) and (401,16) and their PC5 rows are missing there; the table, lemma, pcsynth and analysis stages of run 1 completed, and its `results.csv`, `cellsums.csv` and all `pt_*.csv` are byte-identical to the dev run and to run 2 (checked with cmp/diff). Fix (made after seeing that run, before run 2): D4 inner repeats 1 -> 10, and a ratio whose timed block measured 0 ms is written as NA instead of dividing; `g2_analyze.gp` skips NA ratio rows. Only `g2_semaev.gp` and `g2_analyze.gp` changed (new `SCRIPTS.sha256`; `SCRIPTS.v1.sha256` is the old one). The reported numbers all come from run 2 (`out/`); run 1 is kept as evidence of the failure and is not used in any reported number except where stated.
7. **v3 (post-run addition: operation counts).** The task asked for operation counts as the primary cost metric. `g2_opcounts.gp` (new, not in the preregistration; analysis of recorded tables only) writes `out/opcounts.csv` and `out/opcounts.out`; its stage was appended to `run.sh` after `analyze`, so `run.sh` and `SCRIPTS.sha256` changed (`SCRIPTS.v2.sha256` is the hash list of the run reported in RESULTS.md; `SCRIPTS.sha256` now also lists `g2_opcounts.gp`; the preregistration and all other frozen scripts are byte-identical). `results.json` got an `operation_counts` key (via jq from `out/opcounts.csv`, c=1,2 only). The projection group-operation figure is a textbook double-and-add model, not an instrumented count; polynomial evaluations and field multiplications are not counted. The full `run.sh` was not re-executed for v3 (it would overwrite the recorded wall-time rows on a contended machine); instead `g2_opcounts.gp` was run on the recorded tables and one `g2_tables.gp` cell (p=101, c=1, A) was re-run to confirm that the counts are deterministic (byte-identical pt csv, identical tables csv except the `ms` timing column).
8. **v4 (replication follow-up: results.json provenance and run.sh portability).** An independent replication (`replicate2/`, summary in `VERIFICATION.json`) reproduced every scientific number byte-for-byte (`out/results.csv`, `cellsums.csv`, `opcounts.csv`, `curves*.csv`, `lemma.csv`, `pcsynth.csv`, `semaev_pc5.csv` and the 25 `tables_*.csv` apart from their `ms` column) and differed in two `results.json` places only. (a) The `operation_counts` key was absent from the replicate because item 7 added it by a manual jq step that `run.sh` did not contain: a provenance gap, not a numeric difference (the replicate's totals recomputed from its `out/opcounts.csv` match exactly). Fixed by `add_opcounts_json.sh` (deterministic, reads only `out/opcounts.csv`; reproduces the original block exactly from both the original and the replicate `opcounts.csv`), called from `run.sh` after the `opcounts` stage. (b) `NC3_max_halfwidth` (0.33081254 original, 0.31238348 replicate) is the largest half-width of the 99% t-interval of the D2 / D2c wall-clock timer-null ratio, a timing quantity (load 2.2-3.5 vs 13-15); it is not a count and both values contain 1 in 5/5 cells. The replicate's `run.sh` was also cut by the 30 min limit on a loaded machine (about 8 min unloaded) and finished by running analyze, opcounts and plot by hand; `run.sh` now takes the directory from `G2D` (default unchanged), so a copy can be run without editing. `run.sh` and `SCRIPTS.sha256` changed (`SCRIPTS.v3.sha256` is the previous list; the preregistration and all other scripts are byte-identical). Nothing in the scientific analysis changed; `add_opcounts_json.sh` was verified on copies and was not run against the reported `results.json` (already identical).
