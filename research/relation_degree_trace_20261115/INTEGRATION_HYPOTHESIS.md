# Rust-codebase integration hypothesis

Status: code integration and development qualification. Root-API checks are
pending their separately copied immutable qualifier. No new runtime or IC/rho
result is asserted `[pcc:unverified]`.

## Integration boundary

The algebra now has one implementation in `crates/certified-relations`.
The original study library reexports it and forwards `count-field-ops`.
The root codebase depends on that crate and adds
`crypto_lib::cryptanalysis::f4_fp::certified` using the regular F4 `Poly` type.
No plotting dependency enters the root library through this dependency.

`try_quotient_basis` validates the field/shape, merges repeated input terms
without changing their polynomial, constructs the original-input-certified
basis, then checks its converted representation with F4's existing
input-normal-form and all-S-pair checker. `verify_basis` also binds the exported
polynomials to the retained original-input certificates. Nonapplicability is
an explicit error, so a caller selects any fallback deliberately. The default
F4 engine is unchanged. `observed_solving_degree` stays null.

`trace_relations` accepts the same F4 polynomial representation and invokes
the bounded affine-closure/Hilbert analysis. Its separate reference computation
is a completion oracle and is accounted as discovery; its rows are not free
preprocessing for the quotient constructor. Neither final basis degree nor
quotient dimension is relabelled as solving degree or degree of regularity.

## H1: small quotient survives sharing more points

For the generic paired-f3 cycle family generated by the study, additional
shared points may retain a small univariate quotient and coordinate maps,
while a general F4 solve has a different intermediate matrix workload.
Prediction: the existing three-/four-variable development cases produce the
same complete grevlex basis as the actual root F4 implementation on the
31-bit field. The wide field must preserve exact coefficients, scaled equations,
duplicate terms and original-input certificates across the adapter.
These are development hypotheses `[pcc:unverified]`.

A six-variable fixed-seed development case explicitly reports either a fully
checked basis or an expanded-certificate budget failure. A failure is not
called support for six variables. Nonunit subresultants, disconnected graphs,
larger quotient dimension and certificate expansion are falsifiers/limits,
not reasons to replace seeds or raise caps after seeing a result.

## H2: full-cost advantage over the real Rust F4 path

The runtime question now uses the actual optimized `f4_fp::f4` control,
not the old study's textbook Buchberger denominator. A future qualifier must
charge field/shape admission consistently, conversion, all construction,
expanded certificates, basis computation and matched final checks. Output
is the complete basis of the same original ideal; exact equality and external
CAS agreement remain required. The quotient route's additional proof work is
not subtracted. A tenfold result still requires the entire paired interval
above ten with admitted controls; smaller gains and regressions remain visible
`[pcc:unverified]`.

The regular F4 module documents small-prime scope. Its 31-bit cases are the
native control; the 53-bit field receives exact adapter/certificate checks
and needs a supported mature solver such as Singular for a runtime control.
No implicit extension of F4's documented field range is made. Existing native
counter coverage is incomplete, especially dense quotient writes, so no total
operation or GAE ratio can be inferred from these counters.

Do not execute scientific timing until the required S3 checkpoint and
isolation gates pass. Freeze the new root-codebase runtime qualifier and
pre-call manifest before calls; use fresh holdouts only under a separately
preregistered matched protocol. Earlier standalone timings do not answer H2.
This study has no relation-yield, factor-base/P,Q dependency, logarithm
recovery, whole-ECDLP, below-rho or asymptotic claim.
