## Finding

Fp64::new asserts odd3<=p<2^63 but does not itself establish primality. It computes Montgomery constants, creates a BigUint modulus, builds a129-entry inv_fix Vec and calls compute_sqrt_pre. That helper clones BigUints, allocates exponent vectors, searches z=2,3,... for a nonresidue without a cap, and for v2(p-1)>=16 creates HashMap/Vec chunk tables (256 or4096 entries). These operations happen before a borrowed-field F4 entry can charge them. Existing m2/m3 adapters retain this outer-supervisor setup boundary; don't retrospectively claim their full setup is natively admitted.

PrimeField requires modulus()->&BigUint and sqrt_pre()->&SqrtPre, plus Clone and general conversions. Default legendre/is_square/sqrt depend on valid sqrt data; Fp64 overrides legendre with Jacobi but sqrt still uses the precomputation. Therefore an ordinary Fp64 with placeholder sqrt state, a panic sqrt_pre implementation, returning None for every nonzero sqrt, or a dummy modulus is unacceptable. F4's non-use of sqrt does not erase a public trait obligation. GTowerRing also uses modulus equality; its existing generic APIs should not be changed just to evade those obligations.

## Preferred minimal new-path API: arithmetic-only context, no PrimeField impl

For the NEW dynamic F4 module, use a distinct stack-only Fp64Arithmetic context in fp_backend.rs with private p,n_inv,one,r2 (and p_hi only if lazy accumulation actually used). It has no sqrt state, no inv_fix, no BigUint and no heap allocation. Do NOT implement PrimeField. The new dynamic solver uses concrete &Fp64Arithmetic and its narrow inherent methods; no global trait split and no existing caller migration. This changes the proposed dynamic run(&Fp64,...) signature before it is frozen/implemented. If dynamic source is already frozen against &Fp64, coordinate this amendment with that owner first, preserving old source as historical; don't silently add a second backend or duplicate its loop.

Proposed typed API:

- Fp64Arithmetic::try_new(p:u64, remaining_work:u64, remaining_bytes:u64, original_deadline:Instant, observer:&mut impl FnMut(FieldSetupEvent)->Result<(),()>)->Result<FieldSetup,FieldSetupFailure>.
- FieldSetup { field:Fp64Arithmetic, reserved_work:u64, reserved_bytes:u64, prime_verified:bool }. No heap-bearing report/error.
- FieldSetupStop::{InvalidModulus,Composite,WorkLimit,StorageLimit,Deadline,Observer}. Deterministic numeric events Admitted,Complete carry total reservation; no event strings. No callback after failed admission or failed callback.
- Context methods p(),zero(),one(),from_u64(),to_u64(),add(),sub(),neg(),mul(),sqr(). If dynamic loop needs lazy operations, add wide_zero/from/mul_add/reduce and row kernels by explicit ownership/amendment, not implicit PrimeField trait delegation. For the current planned eager dynamic accumulator these are unnecessary.
- Context has no sqrt/legendre/batch_inv/from_biguint/to_biguint/pow_biguint API. This is an intentionally smaller capability, not an incomplete PrimeField. Canonical coefficient validation belongs to input admission; from_u64 can preserve existing reduction semantics for allu64. Elements are private-field Montgomery words exposed only through the agreed native interface; serialize via to_u64.
- Dynamic inversion remains its already planned charged p-2 binary exponentiation, <=61 squares+61 multiplies, with zero check and proven prime context. Do not introduce inv_fix or an unbounded inverse helper solely for API similarity.

Reuse existing Montgomery kernels: extract Fp64::redc body into one private shared redc64(p,n_inv,t) helper and keep original Fp64::redc delegating byte-for-byte equivalent operations. Reuse neg_inv_u64 unchanged (six Newton rounds), the same r=(2^64 mod p),r2=r*r mod p construction and canonical subtraction. Both contexts call the shared reduction helper. Addition/subtraction/negation remain identical modular formulas, preferably shared helpers where this does not broaden legacy change. No new arithmetic algorithm, no runtime fallback to Fp64::new, no copied field module. Existing Fp64 struct, constructors, sqrt acceleration, public name and PrimeField implementation remain intact.

## Setup admission and exact bound

New dynamic profile validates odd3<=p<=2^61-1 before arithmetic; do not widen to2^63. Original adapter still enforces its wide-prime range separately. Admit a fixed proposed SETUP_WORK=131072 modeled units and SETUP_BYTES=4096 before context construction, primality check or observer. These are per-original-run cumulative reservations, not fresh budgets granted by every recursive solver call. A cached borrowed context is allowed only after the once-per-case setup receipt is bound and charged; no hidden global cache. Subtract setup reservation from the same original F4 work/bytes before passing remaining capacities to native run. A profile with remaining limits below the fixed reservation refuses without a callback or backend invocation.

Source justification for131072: use existing deterministic residual_walk::is_prime_u64, not a new primality algorithm. It checks12 small divisors, factors p-1 in at most60 iterations, then uses at most12 fixed witnesses. Each pow_mod has at most61 iterations with <=122 modular products; each witness suffix has at most60 modular squares. Thus <=12*(122+60)=2184 fixed-width u128 modular products, plus12*61 exponent/control loops,12 divisibility checks and fixed field setup. Reserving48 units per possible product gives104832, plus16384 fixed validation/control/setup units totals121216<131072. The unit counts are modeled operations, NOT retired instructions or a latency bound for software u128 division. Review these constants in implementation. Existing hook_pow adds bounded tally work; its thread-local cells are fixed storage, not an allocating trace. No Miller-Rabin search over primes: reject a composite immediately without replacement/resampling.

4096bytes covers the tiny fixed context/report/events and constructor's fixed temporaries by reservation; no dynamic allocations in this path. The actual Rust stack frame/compiler register spills and process runtime are not measured RSS. If implementation introduces any Vec/BigUint/HashMap/closure-owned allocation, the claim must be revised before acceptance. Callback-owned memory is independently admitted by caller. Context Clone/Copy, if exposed, must be explicitly charged for retained copies in the dynamic engine; no uncharged cloning at each recursion.

Check original_deadline at entry, after admission callback, before/after the finite primality check and before Complete. is_prime_u64 has no deadline callback internally, so its bounded2184-product pass is a finite cooperative chunk; do not claim hard deadline preemption. Outer worker supervisor remains. If policy requires checks within witness loops, add a bounded variant of the existing primality helper in residual_walk.rs only under separate ownership, sharing exact witness/kernel logic; do not reimplement it in the adapter. No fresh duration deadline and no full-budget reset after a failed setup. Observer failure after field construction returns a failure without usable field publication.

## Alternative when retaining PrimeField is required

A new Fp64::try_new_bounded could return a fully valid Fp64 while keeping sqrt chunks=None: sqrt_generic already falls back to correct classic Tonelli-Shanks, so optional chunk omission is semantically valid, including largev2(p-1). All exponents, s, non_residue and z_q still must be genuine; even p=3mod4 still needs valid nonresidue for other public methods such as sqrt_tonelli_shanks_plain. Cap candidate z search explicitly (for example at256 tested candidates) and return NonResidueLimit if none found, never call unbounded new on refusal. Use bounded u64 exponentiation and per-candidate charging/deadline checks, capped129 inverse table and fallibly reserved exponent vectors.

However BigUint modulus construction and generic Clone/from_biguint conversions allocate through infallible num-bigint APIs, and constructing a complete backend requires a careful allocator contract beyond byte precharging. A modeled bounded constructor is not automatically allocation-fallible. Do not advertise Allocation rejection for allocations that can still abort. A proper version must audit the exact dependency construction path or explicitly retain that limitation under supervisor. This is more invasive and unnecessary for the new dynamic arithmetic-only loop. If chosen, square-root values need only satisfy r²=a and validity, not identical root sign or performance to chunked legacy; preserve old new() behavior exactly.

5. End-to-end dynamic gate: setup receipt bound once, remaining budget really reduced, recursive native calls share remaining total; field modulus mismatch/input canonical tampering rejected before conversion. No nontrivial native invocation claimed if setup/admission fails.
6. If full bounded Fp64 alternative is chosen instead, additionally test genuine sqrt/Legendre/plainTS for p3mod4,p1mod4 and high2-adicvaluation, cap/refusal at known nonresidue position, optional chunks absence and exact inverse-table behavior. These are not needed for an arithmetic context that exposes no square-root capability.
