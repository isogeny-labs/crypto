# Endpoint and chat recovery repair

A ready replacement could remain unreachable because the address controller
attempted to broaden the instance pool before reconciling the Elastic IP. A
denied launch-template update aborted the invocation. Pool expansion after
legacy workload completion is now best effort; failure retains the current
restrictions and continues through the existing ownership and readiness fences.
Failure to enforce a restriction for unfinished work still stops reconciliation.

The incident also exposed independent chat-recovery failures:

- Completed dependency services removed a runtime directory shared with Codex.
  All recovery units now preserve that directory until reboot.
- Missing inventory entries and archived chats blocked otherwise recoverable
  chats. Missing work is retained in a private per-owner report; archived chats
  remain archived. Recovery checks the latest persisted turn before starting
  another turn, preserving completed and failed outcomes.
- The desktop could launch its app server before the recovery supervisor.
  Recovery now reuses that server without spawning a competing process or
  terminating a server it does not own.
- SQLite backup inherited WAL mode while writing directly to EFS. It now makes
  and validates a local backup, closes it in rollback-journal mode, and copies
  the standalone database into the durable generation. The current-generation
  pointer still advances only after all files and their manifest are committed.

These changes do not extend experiment deadlines, restart completed work, answer
pending approvals, or relax source ownership fencing. Missing enrollment is an
explicit unresolved condition, not evidence that its work was recovered.

Validation includes the Linux infrastructure suite, an online WAL backup and
restore with later source writes, controller-denial regression tests, archived
and missing enrollment handling, latest-turn eligibility, and reuse of an
existing app server. Deployment verification must separately establish the IP
association, desktop connection, fresh model/tool activity, a committed durable
snapshot, and the runtime selected for future workers.

An account policy that denies non-Spot `RunInstances` can also deny Auto Scaling's
launch-template permission validation. A controller repair alone does not prove
that a new worker runtime was rolled out. Keep that deployment qualification
separate, and preserve the account's Spot-only requirement when resolving it.

A later replacement exposed another lifetime mismatch: retained disks can outlive
EC2's terminated-instance records. The controller now writes confirmed death
evidence under the retired instance ID. A worker also persists this evidence
before replacing an ownership row, closing the race with the scheduled controller.
These receipts retain the original-source identity and require conditional writes;
missing EC2 records, expired heartbeats, and an authorized live-source release
never become fabricated termination evidence. The private retained-disk adapter
uses this receipt while keeping encrypted-volume identity and detachment checks.

Bootstrap starts enabled services asynchronously. A slow provider snapshot can
exceed one recovery attempt and be retried by systemd; that first failure must
not abort the bootstrap script before compute readiness can be published.
Publishing compute readiness does not bypass the controller's independent
workload ownership and readiness requirements for endpoint cutover.
